# feat-032 要求仕様書: render_keypoints.py の NPZ 入力対応

## 1. プロジェクト概要

- **何を作るのか**: `phase4/render_keypoints.py` のキーポイント入力として、既存の C3D に加えて NPZ（リフトアップ済み3Dキーポイント）を直接読み込めるようにする
- **なぜ作るのか**: NPZ は 2D→3D リフトアップパイプラインの一次成果物だが、`render_keypoints.py` は C3D しか受け付けないため、`npz_to_c3d.py` での変換ステップが毎回必要になっている。この変換を不要にして検証ワークフローを短縮する
- **誰が使うのか**: 本プロジェクトの開発者・研究者（てんかん患者観察研究の映像検証を行う）
- **どこで使うのか**: phase4 venv（torch/gsplat 必須、`TORCH_CUDA_ARCH_LIST="9.0+PTX"` 環境変数必須）。Linux + CUDA GPU

## 2. 用語定義

機能設計書・コード内でも同じ用語を使う。

| 用語 | 定義 |
|---|---|
| NPZ | numpy 圧縮アーカイブ。本件では `x3d_world`（world座標[m]の3Dキーポイント）を格納したリフトアップ成果物を指す |
| world座標 | NPZ の `x3d_world` の座標系。メートル単位。`render_keypoints.py` のキャリブ座標と同一（feat-018 で確立） |
| キャリブ座標 | キャリブレーションTOML（R, t, K）が定義される座標系。メートル単位。PLY のネイティブ座標と同一 |
| C3D raw座標 | C3D ファイルに格納される生座標。ミリメートル単位。キャリブ座標との関係は `c3d_to_calib`（`(px,py,pz)mm → (pz,px,py)×0.001 m`） |
| frames_data | `render_keypoints.py` 内部のフレーム列表現。各要素 `{"frame_no": int, "data": (n_markers,3) float64 mm, "residual": (n_markers,) float64}` |
| residual | C3D 由来の有効性指標。`residual < 0` のマーカーは無効サンプル（描画スキップ） |
| frame_ids | NPZ の絶対フレーム番号配列（昇順連番、int） |
| pnp_ok | NPZ のフレーム単位フラグ。True = 顔キーポイントを solvePnP で推定、False = body-prior 補完。**本機能では使用しない（無視する）** |
| 既知マーカー | `KEYPOINT_NAMES` の28点（Halpe26 + Spine/Thorax）。入力に無い既知マーカーは描画スキップ（欠損許容、feat-021） |

## 3. 機能要求一覧

### FR-001: NPZ 入力の受け付け（拡張子による自動判別）

- **機能名**: キーポイント入力形式の自動判別
- **概要**: 位置引数のキーポイントファイルパスの拡張子で入力形式を判別し、NPZ と C3D の両方を読み込める
- **入力**: 位置引数 `keypoints_path`（ファイルパス）。パス末尾が `.npz`（大文字小文字を区別しない。`.NPZ` も NPZ 扱い）なら NPZ、それ以外はすべて C3D として読む
- **出力**: 判別結果に応じたローダーで frames_data を構築し、以降は既存の描画パイプライン（投影・オクルージョン・PNG/MP4出力）をそのまま実行する
- **受け入れ基準**:
  - `.npz` パスを渡すと NPZ ローダーが呼ばれ、`.c3d` パスを渡すと従来の C3D ローダーが呼ばれることをユニットテストで確認できる
  - 既存の C3D 入力の動作（feat-015〜024 のテスト）が全件パスを維持する
- **優先度**: Must

### FR-002: NPZ の読み込みと検証

- **機能名**: NPZ 読み込み・入力検証
- **概要**: NPZ を読み込み、正規化・検証する。不正な NPZ はエラーメッセージを出して終了する
- **入力**: NPZ ファイル。必須キー: `x3d_world`, `frame_ids`, `joint_names`。任意キー（読み込むが使用しない）: `pnp_ok`, `center_frame`, `coord_system`
- **正規化**（feat-018 で実装済みの `npz_to_c3d.load_npz` の既存仕様を踏襲し、これを本要求の正とする）: `x3d_world` は float64 化、`frame_ids` は 1次元化（reshape(-1)）+ int64 化、`joint_names` は 1次元化 + 各要素の str 化。この正規化で解釈できる入力（例: `frame_ids` が (F,1) 形状や float dtype）はエラーにせず受け付ける
- **検証**（正規化後に実施）: (1) 必須キーが存在する (2) `x3d_world` が3次元かつ第3軸の長さが3 (3) `frame_ids` / `joint_names` の長さがそれぞれ F / J と一致する (4) `frame_ids` が昇順連番（F≥2 のとき差分すべて1） (5) F≥1
- **出力**: 検証済みの (x3d_world, frame_ids, joint_names)。検証失敗時、および NPZ 読み込み自体の失敗（ファイル不存在、zip 破損、非 NPZ バイナリ、切り詰められたファイルを含む、読み込みで送出されるすべての例外）は、エラーメッセージを stderr に出力し終了コード 1 で終了する。Python のトレースバックで異常終了しない
- **受け入れ基準**: 次の各異常系で main の戻り値が 1 になり stderr にメッセージが出ることをユニットテストで確認できる: 必須キー欠落 / `x3d_world` 形状不正 / `frame_ids` 長さ不一致 / `joint_names` 長さ不一致 / `frame_ids` 非連番 / F=0 / 壊れた NPZ ファイル（非 zip のゴミバイト） / ファイル不存在
- **優先度**: Must

### FR-003: 座標系の整合（world座標 → 既存パイプライン）

- **機能名**: NPZ world座標の既存パイプラインへの接続
- **概要**: NPZ の `x3d_world`（world座標[m]）を、既存パイプラインが期待する C3D raw座標(mm) に変換して frames_data を構築する。既存の `c3d_to_calib` を通した最終的なキャリブ座標が、NPZ の world座標と数値的に一致する
- **入力**: `x3d_world` (F, J, 3)、world座標[m]
- **出力**: frames_data（`data` は C3D raw座標(mm)、float64）。変換は `world_to_c3d_raw`（`(X,Y,Z)m → (Y,Z,X)×1000 mm`、feat-018 で `c3d_to_calib(world_to_c3d_raw(w)) == w` を確立済み）を用いる
- **受け入れ基準**: NPZ の world座標値 w に対し、パイプライン内で `c3d_to_calib` を通した結果が w と一致（許容誤差 1e-9 m 以下）することをユニットテストで確認できる
- **優先度**: Must

### FR-004: 有効性フラグ（residual）の合成

- **機能名**: NPZ 関節の有効/無効判定
- **概要**: NPZ には C3D の residual に相当する情報が無いため、座標値から合成する。フレーム単位の `pnp_ok` は使用しない（全フレーム描画。ユーザー決定 2026-08-13）
- **入力**: 変換後の座標 (F, J, 3)
- **出力**: residual (F, J) float64。関節の座標3成分がすべて有限（NaN でも Inf でもない）なら `0.0`（有効）、1成分でも非有限なら `-1.0`（無効）
- **受け入れ基準**:
  - NaN を含む関節が valid=False（描画スキップ）になることをユニットテストで確認できる
  - `pnp_ok=False` のフレームでも座標が有限なら描画されることをユニットテストで確認できる
- **優先度**: Must

### FR-005: フレーム番号の扱い

- **機能名**: NPZ 絶対フレーム番号の採用
- **概要**: NPZ の `frame_ids`（絶対フレーム番号）を C3D の frame_no と同格に扱う
- **入力**: `frame_ids` (F,)
- **出力**: 連番PNG ファイル名 `frame_{frame_id:06d}.png`（frame_id が 6桁を超える場合は桁あふれせずそのまま全桁出力する。既存 C3D 経路の書式 `{:06d}` と同一）。`--start-frame` / `--end-frame` は frame_ids 基準（両端含む）でフィルタする
- **受け入れ基準**: frame_ids が 145599〜145898 の NPZ に `--start-frame 145700 --end-frame 145710` を指定すると 11 フレームが対象になることをユニットテストで確認できる
- **優先度**: Must

### FR-006: MP4 フレームレートの決定

- **機能名**: NPZ 入力時の MP4 fps 決定
- **概要**: NPZ にはフレームレート情報が無いため、C3D rate 取得不能時の既存フォールバックに合流する
- **入力**: `--mp4-fps`（任意）
- **出力**: `--mp4-fps` 指定時はその値を使用する。未指定時は fps=30.0 を使用し、警告「警告: 入力にフレームレート情報がないため MP4 fps=30 を使用」を stderr に出力する（既存の C3D rate 取得不能時の警告文言を、C3D 固有表現から入力形式非依存の上記文言に変更する）
- **受け入れ基準**: NPZ + `--mp4` で `--mp4-fps 25` 指定時に fps=25、未指定時に fps=30 と警告出力になることをユニットテストで確認できる
- **優先度**: Must

### FR-007: CLI 表記・メッセージの更新

- **機能名**: 位置引数名・ヘルプ・エラーメッセージの NPZ 対応表記
- **概要**: 位置引数 `c3d_path` を `keypoints_path` に改名し、モジュール docstring・ヘルプ・エラーメッセージを「C3D または NPZ」を受け付ける表記に更新する
- **入力**: なし（表記変更）
- **出力**: `--help` の位置引数名が `keypoints_path` になる。`--no-keypoints` 併用時のエラーメッセージ内の `c3d_path` 表記も `keypoints_path` に変わる。既存テスト `tests/test_feat024_distort_render.py` のメッセージ assert（`"c3d_path" in err`）を `"keypoints_path" in err` に追随させる
- **受け入れ基準**: `--help` 出力に `keypoints_path` が含まれ、`uv run pytest -v` が全件パスする
- **優先度**: Should

## 4. 非機能要求

- **パフォーマンス**: NPZ 読み込み・変換の追加時間は、テストデータ（300フレーム×22関節）で 1 秒未満（numpy 一括処理）。レンダリング部の性能は既存 C3D 経路と同一（変更しない）
- **対応環境**: phase4 venv（Python 3.10、torch/gsplat/CUDA 必須）。ユニットテストのうちレンダリングを伴わない部分は root venv（`uv run pytest`）で実行できること（既存テストと同じ方式: `sys.path` に `phase4/` を追加して import する）
- **信頼性**: 不正な NPZ は重い処理（PLY 読み込み・torch import）の前に検出して終了する（既存 C3D 経路と同じ順序）
- **セキュリティ**: 該当なし（ローカルファイル処理のみ）

## 5. 制約条件

- **使用必須**: numpy（既存依存）。NPZ 検証・座標変換は `phase4/npz_to_c3d.py` の既存関数 `load_npz` / `world_to_c3d_raw` を import して再利用する（重複実装を追加しない）
- **使用禁止**: 新規ライブラリの追加は行わない
- **ネットワーク制約**: なし（オフライン動作）
- **ファイルサイズ・メモリ**: 全フレームをメモリに保持する既存方式を踏襲する（テストデータ 300×22×3 float64 ≈ 160KB であり制約にならない）
