# 要求仕様書: feat-045 スマートフォン静止画のカメラパラメータ推定ウィザード

## 1. プロジェクト概要

- **何を作るのか**: 対話式の CLI ウィザード `phase4/estimate_wizard.py`。スマートフォン静止画 1 枚について、2D 点を打てる範囲の画像の書き出し、2D・3D 基準点の確認、入力のコピー、共用設定YAMLの作成を行い、既存の 3 ツール（書き出し `extract_photo_info.py` → 前処理 `prepare_phone_photo.py` → 推定 `estimate_intrinsics_loop.py`）を順に実行する
- **なぜ作るのか**（ユーザー、2026-11-26）: 推定のために設定YAMLを書き、ファイル名・ディレクトリ名を決め、入力を置き場所にコピーする作業が煩雑なため。既存の仕組みはそのまま使い、ウィザードを追加する
- **誰が使うのか**: 本プロジェクトの研究者。Windows 11 の WSL2 上の Ubuntu 24 で、GPU（RTX 5070 Ti / 5060 Ti）のある PC で実行する
- **範囲外**: 2D 点を打つ作業そのもの（今までどおり人が GIMP で原本に打つ）、既存 3 ツールの変更、実行環境の構築

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 原本 | スマートフォンで撮ったままの JPEG（例: 4000x3000） |
| 打てる範囲 | 原本の画素座標で、前処理の座標変換（16:9 への切り抜き・1920x1080 への縮小、画素中心規約）の後も前処理後画像の範囲内（0 ≤ x ≤ 1919、0 ≤ y ≤ 1079）に入る点の範囲。整数の画素座標で表すと、4000x3000 なら x=1〜3998、y=376〜2623（切り抜きの上端 y=375 と最下行 y=2624 は含まない。端の画素は縮小後に範囲外へ出るため）。この外に打った 2D 点は前処理で除かれる |
| 範囲画像 | 原本に打てる範囲を描き込んだ画像（範囲外を暗くし、境界に線と y 座標の文字を描く） |
| 確認画像 | 範囲画像の上に 2D 点と名前の番号を描いた画像 |
| ジョブフォルダ | ウィザードが 1 回の推定のために作るフォルダ。入力のコピー、範囲画像、確認画像、共用設定YAML、3 ツールの出力をすべてここに置く。場所は `phase4/data/EIL/{作業フォルダ名}/`（ウィザードが決める。`phase4/data/` は git 管理外）。画面上は「作業フォルダ」と表示する |
| 共用設定YAML | 3 ツールに `--config` で渡す設定YAML（feat-043 / feat-044） |
| 2D 点 CSV / 3D 基準点 CSV | `points_2d.csv` 形式（`ObjectName,camera_name,X,Y`。原本の画素座標）/ `kijunten_locations.csv` 形式（`ObjectName,X,Y,Z`） |

## 3. 機能要求一覧

### FR-001: 原本と作業フォルダ（ジョブフォルダ）の指定

- **概要**: 原本のパス、作業フォルダの名前、カメラ名を対話で受け付け、ジョブフォルダ（`phase4/data/EIL/{名前}/`）を作って原本をコピーする
- **詳細**:
  - 原本は、ウィザードが後で実行する書き出し・前処理が受け付ける画像であること。**人が 2D 点を打つ前に**、既存ツールと同じ判定で次をすべて確かめ、満たさなければ理由を表示して原本を聞き直す:
    - 開ける画像で、前処理と同じ規則で 16:9 に切り抜ける大きさ（幅が 16 の倍数、高さ ≥ 幅×9/16）
    - 前処理の Exif 検査に合格する（Orientation が無いか 1、横長、DigitalZoomRatio が無いか 1.0）
    - Exif に 35mm 換算焦点距離（0 より大きい値）がある（書き出しが成功する条件）
  - Exif の無い画像（35mm 換算焦点距離が無い画像）は、ウィザードの対象外とする。その場合は、写真情報ファイルを手で書き、既存の前処理・推定を手で実行する（feat-044 の手順）。ウィザードはその旨を表示する
  - 作業フォルダは**パスではなく名前だけ**を受け付ける（2026-11-26 手動テストでのユーザー指摘。investigation.md イテレーション1）。場所はウィザードが `phase4/data/EIL/{名前}/` に決める（CLAUDE.md「テストデータ」の規則: データは各 phase の `data/` に置く。git 管理外）
  - 名前を聞く前に、何のためのフォルダかを表示する: ウィザードが `phase4/data/EIL/` の下に新しく作ること、入力のコピー（PLY を含む）・確認用の画像・設定ファイル・3 ツールの出力をすべて保存すること
  - 名前は英数字・`_`・`-` だけからなる 1 文字以上（正規表現 `^[A-Za-z0-9_-]+$`。例 `20261126-01`）。違反、または `phase4/data/EIL/{名前}` が既に存在する場合は理由を表示して聞き直す。`phase4/data/EIL/` が無ければ作る。作ったら作業フォルダの絶対パスを表示する。作る前に、絶対パスに改行・前後の空白がある場合（共用設定YAMLに書けない）は、理由を表示して終了コード 1（作業フォルダは作らない）。`phase4/data` と `phase4/data/EIL` は通常のディレクトリである前提とし、シンボリックリンクの場合の置き場所は検査しない（ユーザー判断 2026-11-26）
  - カメラ名を聞く前に、何に使う名前かを表示する（初期 TOML・2D 点 CSV・推定結果でこの写真を指す名前。使える文字）
  - PLY を聞くときは、3DGS の PLY であることが分かる文言にする
  - カメラ名は、前処理が書く初期 TOML のテーブル名（`[カメラ名]`）・2D 点 CSV の `camera_name`・前処理後画像のファイル名のすべてでそのまま使える名前に限る: 英数字・`_`・`-` だけからなる 1 文字以上の名前（正規表現 `^[A-Za-z0-9_-]+$`。TOML の裸のキーに使える文字）で、先頭が `-` でなく（推定が最終精緻化に `--cameras <カメラ名>` として渡すため、`-` で始まると引数と解釈される）、`metadata` でない（最終精緻化が TOML の `[metadata]` を特別に扱うため）こと。満たさなければ入力し直し
  - カメラ名の既定値は原本のファイル名から拡張子を除いたもの（Enter で採用）。それが上の規則を満たさない場合は既定値を出さない
- **受け入れ基準**:
  1. 新しい作業フォルダ名を答えると `phase4/data/EIL/{名前}/` が作られ、原本がコピーされる（中身がバイト単位で同じ）。リポジトリ直下など他の場所には作られない
  2. 規則違反の作業フォルダ名（例: `a/b`、`../x`、`a b`）、既にある作業フォルダ名、切り抜けない大きさの画像、Exif 検査に不合格の画像、35mm 換算焦点距離の無い画像、規則違反のカメラ名（例: `cam 1`、`写真`、`cam.1`、`-cam`、`metadata`）は、それぞれ理由を表示して同じ項目を聞き直す。原本の判定は範囲画像を書き出す前に行う

### FR-002: 範囲画像の書き出し

- **概要**: 原本に打てる範囲を描いた範囲画像をジョブフォルダに書き出し、そのパスと 2D 点 CSV の書式を表示して、人が GIMP で 2D 点を打つのを待つ
- **詳細**:
  - 打てる範囲は、前処理と同じ計算（`compute_crop` と座標変換 `convert_point`、前処理の範囲判定）で求める
  - 打てる範囲の外を暗くし、範囲の上端・下端の行に線を引き、線の近くに `y=上端` / `y=下端` の文字を描く（先行例 `phase4/data/10F/s25_original/20261124_152436_crop_area.jpg` と同じ形。左右の端の各 1 列も範囲外として暗くする）
  - 表示する内容: 範囲画像のパス、打てる範囲（x・y それぞれの最小・最大の整数座標）、2D 点 CSV の書式（列名、`camera_name` に書く値＝カメラ名、座標は原本の画素座標）
- **受け入れ基準**:
  1. 4000x3000 の原本で、x=1〜3998・y=376〜2623 の外が暗くなり、y=376 と y=2623 に線と文字がある画像がジョブフォルダにできる
  2. 範囲画像の範囲の内側の画素は原本と同じ値（暗くしない。線と文字の部分を除く）
  3. 打てる範囲の整数座標は、前処理の座標変換と範囲判定で範囲内になる点とちょうど一致する（範囲の端の内側の点は範囲内、外側の点は範囲外）

### FR-003: 2D・3D 基準点の確認

- **概要**: 2D 点 CSV と 3D 基準点 CSV のパスを受け付け、名前を照合し、確認画像で人に確認してもらう
- **詳細**:
  - 2D 点 CSV と 3D 基準点 CSV は UTF-8 で書かれていること。既存の読み込み規則で読む（UTF-8 として読めないファイルは誤り。必須列、座標が有限の数値、2D は (camera_name, ObjectName)・3D は ObjectName の重複を誤りとする）
  - 2D 点 CSV からカメラ名の行だけを取り出す。1 行も無ければ誤り
  - 名前（ObjectName）を照合し、「両方にある名前」「2D にだけある名前」「3D にだけある名前」を表示する。**2D にだけある名前があれば誤り**。3D にだけある名前は表示だけ（写っていない点）
  - ObjectName に `,`・`"`・改行文字を含む 2D 点があれば誤り（前処理は 2D 点 CSV を引用符なしで書き出すため、推定がその CSV を正しく読めない）
  - 2D 点ごとに、前処理と同じ判定で打てる範囲の内か外かを調べ、範囲外の点（前処理で除かれる点）の名前を表示する。**範囲内の点が前処理の必要数（6 点）未満なら誤り**（前処理が終了コード 1 になるため）
  - 確認画像: 範囲画像の上に、カメラ名の 2D 点を `phase0/visualize_points_2d.py` と同じ描き方（赤い円・黄色い中心点・ObjectName の最後の数字列のラベル〔黒縁の緑文字〕）で描いてジョブフォルダに書き出す。ラベルは常に描く
  - 確認画像のパスを表示し、「点の位置と名前は正しいですか」を y/n で聞く
  - 誤りのとき、または n のときは、2D 点 CSV と 3D 基準点 CSV のパスを聞き直す（前回の値を既定値にする）。ウィザードを最初からやり直す必要はない
- **受け入れ基準**:
  1. 2D にだけある名前がある、2D 点の重複がある、カメラ名の行が無い、ObjectName に `,`・`"`・改行文字がある、範囲内の点が 6 点未満、のいずれかで、理由を表示して 2 つの CSV のパスを聞き直す
  2. 照合が通ると確認画像ができ、y で次へ進み、n で 2 つの CSV のパスを聞き直す
  3. 確認画像の点の位置は 2D 点 CSV の座標（原本の画素座標）と一致する

### FR-004: 入力のコピーと共用設定YAMLの作成

- **概要**: 確認済みの 2D 点 CSV・3D 基準点 CSV と、PLY をジョブフォルダにコピーし、共用設定YAMLをジョブフォルダに書く
- **詳細**:
  - PLY のパスを聞く（存在するファイルであること。中身は検査しない）
  - 2D 点 CSV・3D 基準点 CSV・PLY は、ファイルの中身をそのままジョブフォルダにコピーする（2D 点 CSV は他のカメラの行も含めてそのまま）
  - 共用設定YAMLには、3 ツールが使うすべてのパス（入力のコピー、写真情報ファイル、前処理の出力、推定の出力ディレクトリ）を**ジョブフォルダ内の絶対パスで明示的に**書く。名前はウィザードが決め、ジョブフォルダの構成は機能設計書で定める
- **受け入れ基準**:
  1. コピーした 3 ファイルは元とバイト単位で同じ
  2. 共用設定YAMLを 3 ツールに `--config` だけで渡して動く（キーは 3 ツールが受け付けるものだけ）

### FR-005: 3 ツールの実行

- **概要**: 確認のうえ、書き出し → 前処理 → 推定を順に実行する
- **詳細**:
  - 実行前に、共用設定YAMLのパスと、手で実行する場合の 3 コマンドを表示し（コマンドはシェルにそのまま貼って動くよう、空白などを含むパスを引用符で囲む）、「実行しますか」を y/n で聞く。n なら実行せずに終了する（終了コード 0。ジョブフォルダはそのまま残る）
  - 各ツールは、ウィザードと同じ Python で、`--config <共用設定YAML>` だけを渡して実行する。ツールの出力はそのまま画面に流す
  - ツールが 0 以外の終了コードで終わったら、そこで止め、どのツールが何番で終わったかと、続きを手で実行するコマンドを表示する。続きのコマンドは、原因を直したあとそのまま実行して既存出力の検査で止まらない形にする: 前処理には `--overwrite` を付ける（途中まで書いた出力があり得るため。上書きされるのはジョブフォルダ内の前処理の出力だけ）。推定には、まだ存在しない新しい出力ディレクトリ（`--out-dir`）を指定する（推定は失敗しても出力ディレクトリを作っているため）
  - 3 つとも成功したら、推定の出力ディレクトリを表示する
- **受け入れ基準**:
  1. 10F の実データで、3 ツールが順に実行され、推定の結果（`{カメラ名}_loop.toml`・`{カメラ名}_final.toml`）が同じ入力で手で実行した場合（feat-044 の手動テスト `phase4/data/10F/feat044_out/`）とバイト単位で一致する（比較元のハッシュと、比較元が無い場合の作り方は機能設計書 §6.3）
  2. ツールが失敗すると、後続のツールを実行せずに止まる

### FR-006: 中断と終了コード

- **詳細**:
  - 入力の途中で Ctrl+C または入力の終わり（EOF）になったら、中断した旨と、作成済みならジョブフォルダのパスを表示して終了する（ジョブフォルダは消さない）
  - ウィザードは途中から再開しない。続け方は中断した時点で決まり、中断時に表示する:
    - 共用設定YAMLを書き終える前の中断: 新しい作業フォルダ名で最初からやり直す
    - 共用設定YAMLを書き終えた後、3 ツールを起動する前の中断（実行確認の y/n での中断）: 通常の 3 コマンド（実行確認の前に表示したもの）を表示し、それで続ける
    - 3 ツールの実行中の中断: FR-005 の失敗時と同じく、中断した工程から続ける手動コマンド（前処理に `--overwrite`、推定に新しい `--out-dir`）を表示する
  - 終了コード: 0=成功（3 ツールとも成功、または実行前に n を選んだ）、1=ツールの失敗・ファイル操作の失敗・中断、2=引数エラー（ウィザードは `--help` 以外の引数を受け付けない）

## 4. 非機能要求

- 既存の 3 ツールと、その入出力・終了コードは変更しない
- 新しいライブラリは追加しない（phase4 環境の OpenCV・Pillow・NumPy を使う）
- コメント・出力メッセージは日本語
- 推定に必要な環境変数（`TORCH_CUDA_ARCH_LIST="9.0+PTX"` 等）は、ウィザードを起動するときに人が付ける（ウィザードは子プロセスにそのまま引き継ぐ）

## 5. 制約条件

- phase4 の uv 環境で実行する（`uv run --project phase4 python phase4/estimate_wizard.py`）
- 2D 点 CSV・3D 基準点 CSV の読み込みは既存の関数（`refine_extrinsics.py` の `load_points_2d_csv`・`load_points_3d_csv`）を使う
- 打てる範囲は前処理の `compute_crop` を使う（前処理と食い違わないため）
- `phase0/visualize_points_2d.py` は phase0 の環境にあるため import しない。描き方をウィザード側に同じ形で書く

## 6. 優先順位

すべて必須（FR-001〜FR-006）。

## 7. 使い方（要求レベル）

```bash
# プロジェクトルートで実行（推定に GPU を使うため環境変数を付ける）
TORCH_CUDA_ARCH_LIST="9.0+PTX" uv run --project phase4 python phase4/estimate_wizard.py
```

対話の流れ:

1. 原本のパス、作業フォルダの名前（`phase4/data/EIL/{名前}/` に作られる）、カメラ名（既定は原本のファイル名）を答える
2. 範囲画像のパスと 2D 点 CSV の書式が表示される。範囲画像を見ながら GIMP で原本に 2D 点を打ち、2D 点 CSV を作る
3. 2D 点 CSV と 3D 基準点 CSV のパスを答える。名前の照合結果と確認画像のパスが表示されるので、確認画像を見て y/n を答える
4. PLY のパスを答える。入力がジョブフォルダにコピーされ、共用設定YAMLが書かれる
5. 「実行しますか」に y と答えると、書き出し → 前処理 → 推定 が順に実行される
