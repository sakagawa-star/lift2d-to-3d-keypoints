## 1.1 プロジェクト概要

- **何を作るのか**: 巨大NPZ（5〜10時間分のリフトアップ済み3Dキーポイント）を直読みし、頭部キーポイントから一人称視点（FPS）カメラポーズを計算して、3DGS（PLY）シーンを gsplat でレンダリングした1本のMP4動画を生成するバッチプログラム `phase4/render_fps_video.py` を新規作成する
- **なぜ作るのか**: 現行の FPS 動画生成フロー（NPZ → C3D → Blender 取り込み → `fps_camera_pose.py` → ポーズJSON → `render.py`)は Blender の手動工程を含み大量生産できない。また C3D はヘッダ16bit制約（30fpsで約36分）で長時間データを保持できない。Blender・C3D 工程を廃止して手動作業ゼロにする
- **誰が使うのか**: 本プロジェクトの研究者（てんかん患者観察研究の映像解析）
- **どこで使うのか**: 本番は A100 サーバー（GPU 7枚、研究室共用・申請制、SSH直接実行、Slurm 非依存）。開発・デバッグはローカル機（RTX 5060 Ti）

## 1.2 用語定義

機能設計書・コード内でも同じ用語を使う。

| 用語 | 定義 |
|---|---|
| NPZ | `npz_to_c3d.py` の入力と同一規約の NumPy 圧縮アーカイブ。必須キー `x3d_world (F,J,3)` ワールド座標[m]・`frame_ids (F,)` 絶対フレーム番号（昇順連番）・`joint_names (J,)` |
| frame_id | NPZ の `frame_ids` に格納された絶対フレーム番号（元映像のフレーム番号。連番だが 0 始まりとは限らない） |
| 頭部7点 | 関節名 LEye, REye, LEar, REar, Nose, Head, Neck の7関節 |
| 一次視線 | 耳中点→鼻ベクトルを両目軸に直交化した前方ベクトル（`fps_camera_pose.py` FR-001 の式が正本） |
| c2w | camera-to-world 4x4 同次変換行列 |
| Blenderカメラ規約 | カメラローカル +X右, +Y上, -Z前方（ローカル +Z=後方） |
| OpenCVカメラ規約 | カメラローカル +X右, -Y上（=+Y下）, +Z前方 |
| viewmat | world-to-camera 4x4 行列（OpenCV規約）。gsplat `rasterization` に渡す |
| 黒フレーム | カメラポーズが計算できないため全画素 RGB=(0,0,0) で出力するフレーム |
| 縮退 | 一次視線計算の正規化前ベクトル長が EPS=1e-8 未満、または計算後の回転行列が検証（NaN/Inf・行列式・直交性、許容 1e-6）に失敗する状態 |
| チャンク | 時系列を固定フレーム数で機械分割した区間。区間ごとに1本の区間MP4を生成する |
| 区間MP4 | 1チャンク分のフレームをエンコードした中間MP4ファイル。最終出力はこれらの連結 |
| ピンホールモデル | 歪み係数を使わない投影モデル。K（fx,fy,cx,cy）と width/height のみ使用 |

## 1.3 機能要求一覧

### FR-001: NPZ読み込みと検証

- **概要**: 入力NPZを読み込み、スキーマを検証する
- **入力**: NPZファイルパス（第2位置引数）
- **出力**: メモリ上の `x3d_world (F,J,3) float64`、`frame_ids (F,) int64`、`joint_names（長さJ）`
- **詳細**:
  - `phase4/npz_to_c3d.py` の `load_npz()` を import して再利用する（必須キー存在・形状・frame_ids 昇順連番の検証を含む）
  - F = 0（フレームが1件もない）の場合はエラーメッセージを stderr に出力して終了コード1で終了する（`load_npz()` は F=0 を拒否しないため本プログラム側で検証する）
  - `joint_names` に頭部7点のうち存在しない名前が1つでもあればエラーメッセージ（欠けている名前を列挙）を stderr に出力して終了コード1で終了する
  - 規約外の追加キー（実データに存在する `pnp_ok`, `coord_system` を含む）は読み飛ばし、処理に使用しない（`pnp_ok` の意味が確定するまでの暫定仕様。hearing-notes.md §5-0）
- **受け入れ基準**: 正常NPZで (F,J,3) が得られる。必須キー欠落・形状不一致・非連番・F=0・頭部7点欠落の各ケースでエラーメッセージを出して終了コード1で終了する

### FR-002: カメラ内部パラメータの読み込み

- **概要**: Calib_scene.toml 型 TOML からレンダリングカメラの K と解像度を読み込む
- **入力**: `--toml <パス>`（必須）、`--camera <カメラ名>`（必須）
- **出力**: fx, fy, cx, cy（float）、width, height（int）
- **詳細**:
  - `phase4/render_keypoints.py` の `load_cameras_toml()` / `select_camera()` を import して再利用する
  - 歪み係数 D は読み込むが使用しない（ピンホールモデル。hearing-notes.md 確定要件5）
  - TOML の `rotation` / `translation`（外部パラメータ）は使用しない（外部パラメータは頭部キーポイントから計算するため）
  - width または height が奇数の場合はエラーメッセージを出して終了コード1で終了する（libx264 の yuv420p 制約）
  - 指定カメラ名が TOML に存在しない場合は利用可能カメラ名一覧を表示して終了コード1で終了する
- **受け入れ基準**: 実データ TOML から指定カメラの K・解像度が取得できる。カメラ名不一致・奇数解像度でエラー終了する

### FR-003: カメラポーズ計算（numpy）

- **概要**: 全フレームの頭部7点からFPSカメラの c2w を numpy で計算する
- **入力**: `x3d_world` の頭部7点座標（全フレーム）
- **出力**: c2w（F,4,4）float64（Blenderカメラ規約）、および gsplat 用 viewmat（F,4,4）float32（OpenCV規約）
- **詳細**:
  - 計算式は `fps_camera_pose.py` の `compute_anchor_rotation_euler()` と同一とする（正本）:
    - カメラ位置 = 両目中点（LEye と REye の中点）
    - p = normalize(Nose − 耳中点)、r0 = normalize(LEye − REye)
    - f = normalize(p − r0·(p·r0))（一次視線。両目軸に直交）
    - u = normalize(f × r0)、head_up = normalize(Head − Neck)、u·head_up < 0 なら u を反転
    - b = −f、r = normalize(u × b)、回転行列の列 = (r, u, b)（Blenderカメラ規約、det=+1）
  - 縮退判定の閾値・検証は旧実装と同一とする: 正規化前ベクトル長 < EPS=1e-8（対象: Nose−耳中点、LEye−REye、直交化後 f、Head−Neck）、回転行列の NaN/Inf・|det−1| > 1e-6・直交性偏差 > 1e-6
  - Blender規約 → OpenCV規約の変換は `render.py` の `blender_to_opencv_c2w()` と同一の式（c2w_cv = c2w_b @ diag(1,−1,−1,1)）とし、viewmat = inv(c2w_cv) とする
  - `rotate_z90` 相当の補正は行わない（NPZ の world 座標は PLY と同一のため。hearing-notes.md 確定要件3）
- **受け入れ基準**: FR-012 の等価性検証（案A）に合格する。数式の単体テスト（合成データで既知の向き・符号反転・縮退検出を検証）が全件成功する

### FR-004: フレーム有効性判定（黒フレーム化）

- **概要**: カメラポーズが計算できないフレームを黒フレームとして出力し、タイムライン（動画時刻＝実時刻）を維持する
- **入力**: 全フレームの頭部7点座標
- **出力**: フレームごとの有効/黒の判定マスク（F,）と黒理由（NaN / 縮退）
- **詳細**:
  - 黒フレームの条件（いずれかを満たす）:
    1. 頭部7点のいずれかの座標に非有限値（NaN または Inf）を含む（全点NaN・部分NaN とも同じ扱い。2026-08-07 ヒアリング確定）
    2. 縮退（用語定義参照。2026-08-07 ヒアリング確定: 旧実装のエラー終了から変更し、バッチを完走させる）
  - 条件1（NaN）は正常な欠損（人の不在）として警告を出さず、件数のみサマリに出力する
  - 条件2（縮退）は警告として frame_id と理由（どのベクトルが縮退したか、または回転検証のどれに失敗したか）を1件ずつ stderr に出力する
  - 頭部7点以外の関節の NaN は判定に使用しない（カメラポーズ計算に不要のため）
- **受け入れ基準**: NaN を含む合成データで該当フレームだけが黒判定になる。縮退データで警告が出力され処理が継続する。実データ（NaN 340フレーム）で黒フレーム数が340になる

### FR-005: チャンク分割と区間MP4レンダリング

- **概要**: 全フレームを固定フレーム数のチャンクに分割し、チャンクごとに gsplat レンダリング＋ffmpeg エンコードで区間MP4を生成する
- **入力**: PLYファイルパス（第1位置引数）、viewmat・判定マスク（FR-003/004）、`--gpu <int>`（デフォルト 0）、`--chunk-size <int>`（デフォルト 10000）、`--fps <float>`（必須）、`--crf <int>`（デフォルト 18）、`--preset <str>`（デフォルト medium）
- **出力**: チャンクディレクトリ配下の区間MP4群（1チャンク=1ファイル）
- **詳細**:
  - チャンクはフレーム配列の先頭から `--chunk-size` フレームずつの固定長で機械分割する（最終チャンクのみ端数可。2026-08-07 ヒアリング確定）
  - 処理は単一GPU（`--gpu` で指定した1枚）でチャンク番号順に直列実行する。指定 GPU ID が実機の GPU 数の範囲外の場合は開始前にエラー終了する
  - PLY はGPUに1回だけロードし、全チャンクで使い回す
  - 有効フレームは gsplat（`render.py` の `load_ply()` / `render_frame()` を import して再利用）でレンダリングし、黒フレームは GPU を使わず黒画像データを直接エンコーダに渡す
  - チャンクが失敗（ffmpeg エラー、CUDA エラー）した場合は後続チャンクを処理せず終了コード1で終了する（完成済みチャンクは残す＝FR-007 で再開可能）
  - エンコードは ffmpeg プロセスに rawvideo（rgb24）をパイプ渡しし、libx264・yuv420p・`--crf`・`--preset` でエンコードする（`render.py` の MP4 出力方式を踏襲。NVENC は使用しない: A100 は NVENC ハードウェア非搭載のため）
  - 区間MP4は一時ファイル名で書き出し、ffmpeg 正常終了後に**ファイル内容を fsync してから** `os.replace` で最終ファイル名に確定する（電源断・OSクラッシュで「確定ファイル名だけ存在して中身が欠損」する事象を防ぐ）
  - 解像度は TOML の width×height、フレームレートは `--fps` とする
  - ffmpeg バイナリが見つからない場合、または ffmpeg に libx264 エンコーダがない場合は、レンダリング開始前にエラー終了する
- **受け入れ基準**: 短い実データ（数百フレーム）で区間MP4が生成され、フレーム数がチャンクのフレーム数と一致する。ffmpeg 不在時に開始前エラーとなる

### FR-006: 複数GPUプロセス並列【本案件から除外・後続案件に分割】

2026-08-07 の人レビューで、複数GPU並列の実装は後続案件に分割すると決定した（実装を小さく保ち、単一GPUで動作確認してから積み上げるため。CLAUDE.md 開発方針に準拠）。本案件は FR-005 の単一GPU直列実装のみとする。後続案件の起票は本案件完了後に行う。番号 FR-006 は他要求のID安定のため欠番として維持する。

### FR-007: 再開（完成済みチャンクのスキップ）

- **概要**: 中断後の再実行で完成済みチャンクをスキップし、途中から再開できる
- **入力**: 前回実行のチャンクディレクトリ、`--overwrite` フラグ
- **出力**: 不足チャンクのみ新規生成
- **詳細**:
  - 実行パラメータ（入力パス、カメラ名、fps、解像度、chunk_size、crf、preset、フレーム範囲）をチャンクディレクトリ内のマニフェストファイルに保存する（区間MP4と同じ fsync 込みの耐久書き出し手順。マニフェストが JSON として読めない場合はエラーメッセージを出して終了コード1で終了する（`--overwrite` で作り直し可能））
  - 再実行時、マニフェストが存在して現在のパラメータと一致する場合のみ、既存チャンクのスキップ判定に進む
  - スキップ判定はファイル名の存在だけで行わない。最終ファイル名が存在するチャンクごとに ffprobe でコンテナメタデータを検査し（全フレームのデコードは行わない）、(a) 読み取り可能で (b) 映像ストリームのフレーム数がそのチャンクの期待フレーム数と一致する場合のみスキップする。検査に不合格のチャンクは「警告: チャンク {番号} が壊れています（{理由}）。作り直します」を stderr に出力してファイルを削除し、再レンダリング対象にする
  - マニフェストが不一致の場合は「パラメータが変更されている」旨のエラーメッセージ（不一致項目を列挙）を出して終了コード1で終了する（`--overwrite` 指定時はチャンクディレクトリを削除して全チャンクを作り直す）
- **受け入れ基準**: 一部チャンク生成後に中断→再実行で、完成済みチャンクが再生成されずに残りが生成される。完成済みチャンクの1つをファイル途中で切り詰めて壊した状態で再実行すると、当該チャンクだけ警告つきで作り直される。chunk_size を変えて再実行するとエラー終了し、`--overwrite` で作り直せる

### FR-008: チャンク連結による最終MP4出力

- **概要**: 全チャンクの区間MP4を連結して1本の最終MP4を出力する
- **入力**: 全区間MP4、`--output <パス>`（デフォルト: 入力NPZと同ディレクトリの `<NPZ名（拡張子除く）>_fps.mp4`）
- **出力**: 最終MP4 1本（総フレーム数 = F、再エンコードなし）
- **詳細**:
  - ffmpeg concat demuxer（`-f concat -c copy`）で再エンコードなしに連結する
  - 連結順はチャンク番号順（フレーム時系列順）とする
  - 最終MP4も一時ファイル名に書き出し、ファイル内容を fsync してから `os.replace` で確定する（FR-005 の区間MP4と同じ手順）
  - 連結成功後、チャンクディレクトリを削除する（`--keep-chunks` 指定時は残す）
- **受け入れ基準**: 最終MP4の総フレーム数が F と一致する（ffprobe で検証）。動画時刻 = (frame_id − 先頭frame_id) / fps が維持されている

### FR-009: デバッグ静止画モード

- **概要**: 指定範囲のフレームを連番PNGで出力する排他モード（MP4 出力なし。hearing-notes.md 確定要件11）
- **入力**: `--still-range <開始frame_id> <終了frame_id>`（両端含む、frame_ids の絶対フレーム番号基準）、`--still-dir <出力ディレクトリ>`（`--still-range` 指定時必須）
- **出力**: `<still-dir>/frame_<frame_id 8桁ゼロ埋め>.png`（範囲内の全フレーム。黒フレームは黒PNG）
- **詳細**:
  - `--still-range` 指定時は MP4 関連処理（チャンク生成・連結）を一切行わない
  - 指定範囲が NPZ の frame_ids 範囲外の場合はエラー終了する（範囲を表示）
  - GPU は `--gpu` で指定した1枚を使用する
- **受け入れ基準**: 指定範囲のPNGが枚数どおり出力され、黒フレーム位置のPNGが全画素 (0,0,0) である。範囲外指定でエラー終了する

### FR-010: ポーズダンプモード

- **概要**: レンダリングせずカメラポーズのみを JSON に書き出す排他モード（FR-012 の等価性検証、および外部ツールでのポーズ確認に使用）
- **入力**: `--dump-poses <出力JSONパス>`
- **出力**: フレームごとの `{frame_id, valid, c2w}` を持つ JSON（c2w は Blenderカメラ規約 4x4。黒フレームは valid=false とし c2w は null）
- **詳細**: `--dump-poses` 指定時はレンダリング・MP4 関連処理を行わない。GPU を使用しない。`--still-range` との同時指定はエラーとする
- **受け入れ基準**: 実データでポーズJSONが出力され、フレーム数が F と一致する

### FR-011: 実行ログ・サマリ

- **概要**: 進捗と統計を標準出力に出す
- **入力**: なし（全モード共通の動作）
- **出力**: stdout のログ（コーディング規約に従い日本語）
- **詳細**: 以下を出力する
  - 開始時: NPZ の F・J・frame_ids 範囲、有効フレーム数・黒フレーム数（NaN 由来と縮退由来を分けて件数表示）、チャンク数と chunk_size、使用 GPU ID、解像度・fps・crf・preset、出力パス
  - チャンク完了ごと: チャンク番号、frame_id 範囲、描画フレーム数/チャンク総フレーム数、所要秒、スキップ時はスキップと明示
  - 終了時: 総所要秒、描画フレームの平均秒/フレーム（描画フレームが0件の場合はゼロ除算せず「N/A（描画0フレーム）」と表示）、最終MP4パスと総フレーム数
- **受け入れ基準**: 実データ実行で上記項目がすべて出力される

### FR-012: 旧パイプラインとの等価性検証（案A）

- **概要**: numpy 移植したカメラポーズ計算が旧 Blender パイプライン（`fps_camera_pose.py`）と等価であることを、実物同士の1回比較で検証する（2026-08-07 ヒアリングで案Aを確定）
- **入力**: 同一データ由来の旧パイプライン出力ポーズJSON（`fps_camera_pose.py` の c2w）と、新実装のポーズダンプ（FR-010）
- **出力**: 検証記録（`docs/issues/feat-027-fps-video-from-npz/experiments/` 配下）
- **詳細**:
  - 比較対象は c2w（位置と回転）のみとする。内部パラメータは比較しない（旧は .blend カメラ由来、新は TOML 由来で入力源が異なるため）
  - 合格基準: 全比較フレームでカメラ位置差の最大 < 1mm、かつ回転角度差の最大 < 0.1°
    - 根拠: 旧経路の数値誤差（C3D の mm float32 丸め ≈ µm オーダー、mathutils の float32 演算）より2桁以上大きく、実装ミス（軸の取り違え・符号誤り等は数十cm・数十°規模）より2桁以上小さい
  - 実施は CLAUDE.md「実験・検証の進め方（予測→実行→照合）」に従う: 実施前に criteria 文書を作成して Codex レビューで lock し、予測→実行→照合を experiment_log.md に記録する
- **受け入れ基準**: 上記合格基準を満たした検証記録が experiments/ 配下に保存されている

| NFR-001 | 対応環境 | Linux + CUDA GPU + ffmpeg / ffprobe（システムバイナリ。通常 ffmpeg と同梱。**ffmpeg は libx264 エンコーダが有効なビルドであること**——非同梱ビルドが実在するため（2026-08-08 ローカル機で確認）実行前に検査する）。本番: A100（sm_80）。開発: RTX 5060 Ti（sm_120、`TORCH_CUDA_ARCH_LIST="9.0+PTX"` が必要。CLAUDE.md 参照）。ポーズダンプモード（FR-010）のみ GPU 不要 |
| NFR-002 | メモリ | NPZ 全体（100万フレーム×22関節×3座標 float64 ≈ 0.5GB）とポーズ配列は全載せ可。レンダリング画像はフレーム単位のストリーミング処理としフレーム数に比例するメモリを使用しない |
| NFR-003 | 信頼性 | 区間MP4・最終MP4はアトミック書き出し（一時ファイル→fsync→`os.replace`）。中断（Ctrl-C・電源断・GPU エラー）後の再実行で完成済みチャンクを失わない。電源断で中身が欠損したチャンクは再開時の ffprobe 検査（FR-007）で検出して作り直す |
| NFR-004 | 性能 | 処理時間の絶対上限は設定しない。代わりに描画フレームの平均秒/フレームをログ出力し（FR-011）、実測に基づく所要時間見積もりを可能にする |
| NFR-005 | ディスク | チャンクディレクトリは連結完了まで最終MP4とほぼ同容量を追加消費する（1080p・CRF18・10時間で概ね30〜60GB）。連結成功後に削除して解消する（FR-008） |

## 1.5 制約条件

- **実行環境**: phase4 の uv 環境（`uv run --project phase4`）。環境操作は uv のみ（pip / venv 直接操作は禁止）
- **使用ライブラリ**: phase4 既存依存（numpy, torch, gsplat, tomli, Pillow）に限定し、新規ライブラリを追加しない。ffmpeg はシステムバイナリを使用する
- **使用禁止**: bpy（Blender Python API）、c3d ライブラリ（本プログラムでは C3D を扱わない）、NVENC（A100 非搭載のため設計から除外）
- **既存スクリプトの変更禁止**: `fps_camera_pose.py` / `render.py` / `render_keypoints.py` / `npz_to_c3d.py` / `filter_npz.py` は変更しない（import による関数再利用は可）
- **入力の前提**: 本プログラムの入力NPZは feat-028（`filter_npz.py`）で平滑化済みであることを想定する（ただし未平滑NPZも同一スキーマなら動作する。平滑化の有無は検証しない）
- **重い依存の import 方針**: torch / gsplat / render.py の import は関数内 import とし、ポーズ計算等の純ロジックが GPU なし環境の pytest で検証できるようにする（`render_keypoints.py` と同じ方針）

## CLI 仕様（要求レベル）

```bash
uv run --project phase4 python render_fps_video.py <ply_path> <npz_path> \
  --toml <Calib_scene.toml> --camera <カメラ名> --fps 30 \
  [--output <出力MP4パス>] [--gpu 0] [--chunk-size 10000] \
  [--crf 18] [--preset medium] [--overwrite] [--keep-chunks] \
  [--still-range <開始frame_id> <終了frame_id> --still-dir <ディレクトリ>] \
  [--dump-poses <出力JSONパス>]
```

| 引数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `ply_path` | ○ | — | 3DGS PLY ファイル |
| `npz_path` | ○ | — | 入力NPZ（平滑化済み想定） |
| `--toml` | ○ | — | Calib_scene.toml 型 TOML |
| `--camera` | ○ | — | TOML 内のカメラ名 |
| `--fps` | ○ | — | フレームレート（float。実データは30） |
| `--output` | — | `<NPZ名>_fps.mp4`（NPZと同ディレクトリ） | 最終MP4パス |
| `--gpu` | — | `0` | 使用GPU ID（単一。複数GPU並列は後続案件） |
| `--chunk-size` | — | `10000` | チャンクのフレーム数 |
| `--crf` | — | `18` | libx264 CRF 値（2026-08-07 ヒアリングで高画質側を確定） |
| `--preset` | — | `medium` | libx264 preset |
| `--overwrite` | — | false | チャンクディレクトリを削除して作り直す |
| `--keep-chunks` | — | false | 連結後もチャンクディレクトリを残す |
| `--still-range` | — | — | デバッグ静止画モード（排他）。frame_id 基準・両端含む |
| `--still-dir` | `--still-range` 時○ | — | PNG 出力ディレクトリ |
| `--dump-poses` | — | — | ポーズダンプモード（排他） |

排他制約: `--still-range` と `--dump-poses` は同時指定不可。いずれかの排他モード指定時、MP4 関連引数（`--output` `--overwrite` `--keep-chunks`）の指定はエラーとする。
