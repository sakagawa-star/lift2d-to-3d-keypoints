# feat-027（仮）: NPZ直読みによる一人称視点動画一括生成 — 事前ヒアリング整理

作成日: 2026-08-07
ステータス: 起票前の参考資料（壁打ちの結論整理。requirements.md 作成の入力とする）

## 1. 目的・背景

- これから**大量の一人称視点（FPS）動画を作る**ため、手動作業を完全になくしたい
- 現行の FPS 動画生成は Blender を経由しており、これを廃止する
- 対象となる現行フロー:
  `NPZ → npz_to_c3d.py → C3D → (filter_c3d.py) → Blender io_anim_c3d 取り込み → blender -b + fps_camera_pose.py → ポーズJSON → render.py → 動画`
- 既存パイプライン（fps_camera_pose.py / render.py / npz_to_c3d.py / filter_c3d.py）は**変更せず温存**し、新プログラムを別途作る（案2を採用。既存を壊さないため）

## 2. 新パイプラインの全体像

```
巨大NPZ (x3d_world, frame_ids, joint_names)
  → [新規①: NPZ時間平滑化スクリプト]  NPZ→NPZ
  → 平滑化済みNPZ
  → [新規②: FPS一括レンダリングプログラム]
       - 全フレームのカメラポーズ計算（numpy。両目中点＋一次視線回転）
       - NaNフレーム＝黒画面としてタイムライン維持
       - 描画対象区間をチャンク分割し複数GPUでプロセス並列レンダリング
       - 黒区間はGPUなしで生成
       - ffmpeg concat で1本のMP4に連結
  → 1本のMP4（5〜10時間）
```

2コマンドをシェルスクリプト等で直列実行すれば手動作業ゼロ。

## 3. 確定要件

| # | 項目 | 決定内容 |
|---|---|---|
| 1 | 入力 | 巨大NPZ（5〜10時間分）を直読み。Blender・C3D工程は使わない |
| 2 | 入力スキーマ | `npz_to_c3d.py` の入力NPZと同一フォーマット（ユーザー確定）: `x3d_world (F,J,3)` ワールド座標[m] / `frame_ids (F,)` 絶対フレーム番号 / `joint_names (J,)`。`load_npz()`（npz_to_c3d.py）が必須キーとして検証しているため `frame_ids` は必ず存在する |
| 3 | 座標系 | NPZ の `x3d_world` は PLY（3DGS）と同一のワールド座標[m]。**座標変換は不要** |
| 4 | 視点生成 | `fps_camera_pose.py` の `compute_anchor_rotation_euler()` と同一の数式を numpy に移植。カメラ位置＝両目中点、向き＝一次視線（耳中点→鼻を両目軸に直交化、Head-Neck で上方向の符号確定） |
| 5 | 内部パラメータ | Calib_scene.toml 型 TOML を引数渡し。`--camera <名前>` でセクション選択。**ピンホールモデル確定**: K（fx,fy,cx,cy）と width/height のみ使用、歪み係数 D は無視 |
| 6 | fps | NPZスキーマに fps 情報なし → CLI 引数で与える。実データの fps は未確認（30 か 60 の見込み） |
| 7 | 欠損区間 | 人が不在の間は NaN 埋め（ユーザー確定）。NaN フレームは**黒画面**として出力し、タイムライン（動画時刻＝実時刻）を維持する |
| 8 | 出力 | **1本の MP4**（ユーザー確定）。連番PNGの全フレーム出力は行わない（100万フレーム規模のため） |
| 9 | 並列化 | A100 サーバー（GPU 7枚、研究室共用・申請制）で実行。使用 GPU は CLI 指定（例 `--gpus 0,1`）。SSH 直接実行、**Slurm 非依存**。区間MP4単位で再開可能（完成済み区間はスキップ）にする |
| 10 | 時間平滑化 | **案B: 独立スクリプト（NPZ→NPZ）として新規作成**（ユーザー確定）。`filter_c3d.py`（feat-020）と同系の Butterworth 2次 filtfilt・ゼロ位相。NaN の扱いも feat-020 と同一: `--max-gap`（既定10フレーム）以下のギャップは補間してフィルタ計算にのみ使い、超えるギャップでセグメント分割して独立に平滑化。出力では NaN を NaN のまま維持 |
| 11 | デバッグ静止画 | FPS レンダリング結果を連番PNGで出す**排他モード**（MP4 出力なし、ユーザー確定）。範囲は `frame_ids`（絶対フレーム番号）ベースの開始・終了で指定。範囲内の NaN フレームは黒PNGを出す |
| 12 | 頭部関節の検証 | `joint_names` に頭部7点（LEye/REye/LEar/REar/Nose/Head/Neck）が存在しない場合はエラー終了 |

## 4. 技術的裏取り結果（再利用できる既存資産）

| 資産 | 場所 | 用途 |
|---|---|---|
| `load_npz()` | `phase4/npz_to_c3d.py` | NPZ 読み込み＋スキーマ検証をそのまま再利用可能 |
| 視線計算の数式 | `phase4/fps_camera_pose.py` の `compute_anchor_rotation_euler()` | mathutils → numpy 移植。縮退検証（EPS）・回転行列検証（det/直交/NaN）も同様に移植する |
| `load_cameras_toml` | `phase4/refine_extrinsics.py` が import して使用 | Calib_scene.toml 型（width/height/K/D 含む）の読み込みを再利用 |
| Butterworth 平滑化 | `phase4/filter_c3d.py`（feat-020） | カットオフ等のデフォルト値を引き継ぐ。C3D I/O 部を NPZ I/O に置き換え |
| レンダリング | `phase4/render.py` | gsplat 呼び出し部を import で再利用（同一 phase4 環境） |
| MP4 出力 | `phase4/render_keypoints.py`（`--no-png` 実装） | ストリーミング MP4 書き出しの参考 |

その他の裏取り事実:

- **C3D を採らない根拠**: C3D はヘッダのフレーム番号が 16bit（`filter_c3d.py` の `MAX_FIRST_FRAME = 65534` に明記）で、30fps 約36分が上限。5〜10時間（30fps で 54万〜108万フレーム）は1ファイルで持てない。NPZ 直読みならこの制約ごと消える
- **メモリ**: 100万フレーム × 22関節 × 3座標 ≈ 数百MB で問題なし。ポーズ計算（numpy）は全フレームでも数秒オーダー
- **黒区間は GPU 不要**: 欠損が長いほど実処理量（記録が存在する時間分のみ）が減る
- **A100 の CUDA 事情**: CLAUDE.md の `TORCH_CUDA_ARCH_LIST="9.0+PTX"` 問題はローカル RTX 5060 Ti（sm_120）固有。A100（sm_80）では通常の wheel で動く見込み
- **filtfilt と NaN**: filtfilt は NaN をまたぐと全体に伝播するため、NaN をそのまま入力できない。feat-020 の確立済み方式（短いギャップは内部補間・長いギャップでセグメント分割・出力は NaN 維持）を踏襲する。また padlen 制約（`filtfilt` 既定 padlen=9、最小10サンプル）により短い有効区間は平滑化できない（→ フィルタ対象から除外で確定）

## 5. 未決事項（requirements.md 作成時に確定する）

2. **fps 引数**: 必須引数にするか、デフォルト 30 を持つか
3. ~~**平滑化の短区間の扱い**~~ → **確定（2026-08-07）**: padlen 未満の有効区間は平滑化せずそのまま出力する（フィルタ対象から除外）
4. ~~**案件分割**~~ → **確定（2026-08-07）**: 2案件に分割。feat-027 = FPS一括レンダリング、feat-028 = NPZ平滑化スクリプト（先行実装）
5. **並列チャンクの粒度・命名**: 区間MP4の分割単位（フレーム数固定か有効区間単位か）、中間ファイルの置き場と再開判定の方式
