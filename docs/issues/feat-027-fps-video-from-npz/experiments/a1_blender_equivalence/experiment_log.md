- 前提チェック P1（旧300フレーム・41〜340連番）: 成立（フェーズ1'' で確認済みの再確認）

- max(d_rot): **1e-4°〜1e-3° オーダー**（float32 正規化ベクトルの角度誤差 + Euler 変換往復。閾値 0.1° の2〜3桁下）

### 実測

- P1 成立 ✓ / P2 成立 ✓
- 位置差: **max = 1.195e-07 m**（frame 235）、mean = 3.750e-08 m
- 回転角度差: **max = 1.533e-02°**（frame 123）、mean = 3.830e-03°
- **判定: 位置 合格（max < 0.001 m）、回転 合格（max < 0.1°）→ 総合 合格**（300フレーム全件、compare_poses.py exit 0）

### 予測との照合

- 判定（合格）: 予測どおり ✓
- 位置差: 予測 1e-6 m オーダーに対し実測 1.2e-7 m（**予測より1桁小さい**。C3D 丸め誤差の見積もりが保守的だった）
- 回転角度差: 予測 1e-4°〜1e-3° オーダーに対し実測 max 1.5e-2°（**予測より1桁大きい**）。原因の理解: 予測は C3D の mm float32 量子化（〜1e-3°相当）のみを主要因と見積もったが、旧経路は Blender 内部の float32 段が多段（アクション F カーブのキー値、アーマチュア評価、制約評価、matrix_world 合成、Euler 変換往復）あり、近接点の差分ベクトル正規化で誤差が増幅される。方向ベクトルの基線長（両目間 約6cm）に対する数µm级の位置誤差で 1e-2° 級の角度誤差は整合的
- 閾値マージンの実際: 回転は閾値 0.1° に対し実測 max の 6.5 倍のマージン（criteria の根拠に書いた「2桁以上」より薄い）。ただし実装ミスの規模（数十°）とは依然 3桁以上離れており、判定の識別力は損なわれていない
- 事後解釈は行っていない: 閾値・合格ラインは locked のまま、全件で満たした
