## 1. 実験の問い（roadmap.md M4 から再掲）

檻環境で「6点手動プロット + 自動リファイン」が成立するか。付随して以下を実測する:

- (b-1) 格子オクルージョンがマッチングをどれだけ削るか
- (b-2) 深度外れ値率（深度ゲート除外率）
- (b-3) 周期誤マッチ（格子の繰り返し構造による準誤マッチ）
- (b-4) 壁際視点のレンダ品質

**測れるものの限界（明示）**: M4 に真値も既存20点方式の基準ポーズも存在しない。M3 criteria §5.4 の確定（独立検証データは確保できない）に従い、M4 の結論は「**診断値ベースの運用受理**」に限定する（実品質の評価とは主張しない）。M3 で使えた一致性判定（20点方式ポーズとの差、M3 criteria §5.3）は M4 では**存在しない**。

| 定数 | 値 | 出典 |

## 5. 初期値の算出とサンプリング手順（固定）

1. **初期値 = 6点PnP（K既知）**: 手動6点を ObjectName でマッチングし、チェスボード較正の K・歪みを固定して `estimate_camera_params.py` の K既知モードと同一経路（`cv2.solvePnPRansac`（閾値8px）→ `cv2.solvePnP(ITERATIVE)` 精密化）で R, t を解く。**M4 が feat-026 の想定運用（6点初期値）を初めて通しで検証する**（M3 は20点方式ポーズ+摂動を初期値に使った）
2. **サンプリング（M3-1 と同一手順・M3-2 と同一判定）**: 初期値3系統のチェーンを実行する
   - チェーン A: 6点PnP 解そのまま（無摂動）
   - チェーン B, C: 6点PnP 解 + 5cm/2° 摂動（`perturb_pose` と同方式、seed 11, 12 = M3 の P1/P2 と同じ）
   - 各チェーン: k=0（緩ゲート）1回 → k≥1 条件で停止せず **N_S=20 回**反復して解を収集
3. **受理判定はチェーン統合型（criteria_m3_2 §1 と同一）**: 3チェーン60サンプルを pooled し、合意クラスタ（r_pos=2.0cm / r_ang=0.30°）の占有率 **f_c ≥ 0.7（=42/60）で受理**。最終解 = pooled クラスタ内サンプルの平均（anchor 相対の回転ベクトル平均）。第2クラスタ占有率 ≥ 0.2 なら「二峰」と分類
4. **二峰時の仲裁（M3 D3 と同一方式。適用条件は §6.2 で数値固定）**: 仲裁対象は**占有率上位2クラスタのみ**。各峰の解（クラスタ内平均）で手動6点を `cv2.projectPoints` し再投影誤差の中央値を比較。**差 ≥ 1.0px なら小さい側を採用**（仲裁成立）。差 < 1.0px なら仲裁不成立=不受理。注意: 手動6点は初期値算出に使用済みでありパイプライン反復には非参照（M3 の手動点と同じ位置づけだが、点数が6と少ないことを記録に明記する）

- 根拠: サンプリング数・クラスタ半径・f_c 閾値・仲裁閾値はすべて M3-1/M3-2/D3 で lock・実証済みの値をそのまま使う（値を動かすと M3 の実証が根拠にならなくなるため動かさない）

## 6. 判定基準（数値固定）

### 6.1 成立性

以下を**すべて**満たせば成立:

1. 6点PnP が解を返す（solvePnPRansac 成功）
2. 3チェーンすべてで k=0 が成立（ゲート後 N_in ≥ 30）し、明示的失敗なく60サンプルを収集できる
3. silent failure がない（失敗する場合は必ず失敗段=マッチ数/ゲート/PnP/発散が特定できる）

- 根拠: N_min=30 は M2/M3 と同値。サンプリング成立の要求は criteria_m3_1 の成立条件と同じ

### 6.2 受理

以下の**いずれか**を満たせば受理:

1. **単峰・高合意**: pooled f_c ≥ 0.7（=42/60）かつ第2クラスタ占有率 < 0.2（criteria_m3_2 の受理条件そのもの）
2. **仲裁成立の二峰**: 以下を**すべて**満たす
   - 第2クラスタ占有率 ≥ 0.2（=12/60。「二峰」の分類条件。根拠: criteria_m3_2 §1 の二峰分類閾値と同値。これ未満の副モードは二峰ではなく、1. の単峰判定に委ねる）
   - 第1クラスタ + 第2クラスタの合計占有率 ≥ 0.9（=54/60。合意が2峰に集中していることの要求。根拠: D3 が仲裁を実証した唯一のケース cam41520554 は 41/60 + 19/60 = 60/60 であり、実証範囲に寄せる。散乱が10%を超えるケースは二峰ではなく多峰/不安定として不受理。なお合計 ≥ 0.9 により第3クラスタ占有率は自動的に ≤ 0.1 となる）
   - 手動点仲裁が成立（上位2クラスタの解の再投影誤差中央値の差 ≥ 1.0px。根拠: D3 の事前閾値と同値）
   - 最終解 = 仲裁で選ばれた側のクラスタ内平均

- 上記のいずれにも該当しない場合（f_c < 0.7 の単峰、仲裁不成立の二峰、2峰に合意が集中しない多峰）は**不受理 = No-Go**
- 根拠: 1. は M3-2 で Go 判定済みの lock 値。2. は D3 で実証した運用フロー（findings §1.10「サンプリング→統合合意→受理/二峰は手動点仲裁」）を M4 の合否に適用するもので、適用条件（対象クラスタ・第3モード禁止・合計占有率・仲裁閾値）を実験前に数値固定した。M3-2 単独基準（二峰=不受理）より緩いが、確立済み運用フローの通し検証こそが M4 の目的であるため、仲裁を受理経路に含める。この判断は lock 時にユーザー承認を得る

### 6.3 (b-1)〜(b-4) の実測（記録。合否には使わない）

| 問い | 計測 | M3 参照値（比較の物差し） |
|---|---|---|
| (b-1) 格子オクルージョン | 段ごとの通過数（生マッチ→ratio→変位ゲート→深度ゲート→RANSAC インライア）を全反復で記録 | 実写生マッチ 258〜446件、N_in ≥ 30 |
| (b-2) 深度外れ値率 | 深度ゲートの除外内訳（NaN / 2×2広がり5%超 / α / z範囲）の件数と率 | M3 実測は `experiment_log.md` 参照 |
| (b-3) 周期誤マッチ | 準誤マッチ率（`m3_diag_quasi.py` と同一定義・同一実装） | 実写 18〜40%（収束カメラ 18〜30%、振動カメラ 37〜39%） |
| (b-4) 壁際レンダ品質 | レンダの有効画素率（α≥0.5）、レンダ/実写それぞれの SIFT キーポイント数と比、レンダ・実写の重畳PNG（目視記録） | 定量参照値なし（M4 で初計測） |

- (b-1)〜(b-4) は記録・切り分け材料であり、合否には使わない。**合否は §6.1・§6.2・§6.4 で判定する**（roadmap: b-1〜b-4 は「実測」が目的）

### 6.4 総合判定の照合（roadmap「M1 × M2/M3 × 受理条件の突き合わせ」。**Go の前提条件**）

- **6点PnP 初期解と最終解（§6.2 で受理された解）の差**（カメラ中心距離・回転角）が、M2 実測収束域 **位置 ≤ 50cm かつ角度 ≤ 10°** の内側にあることを **Go の前提条件**とする
- 根拠: roadmap M4 の総合判定は「M1 の初期誤差分布 × M2/M3 の実測収束域 × M3 で較正した受理条件」の突き合わせと定義されている。初期解と最終解の差が実証済み収束域を超えているのに反復が「収束」した場合、それは実証範囲外の挙動であり、受理しても手法の前提（6点初期値が収束域の内側）の検証にならない。前提条件化により「収束域外なのに Go」の抜け穴を塞ぐ
- あわせて M1 実測の初期誤差分布（良好データ中央値 3〜5cm/1°未満）との比較を記録する（こちらは分布との照合であり記録のみ）

### 6.5 診断値の記録と暫定警告閾値（M3 §5.5 を継承。合否に使わない）

| 診断値 | 暫定警告閾値 | 根拠 |
|---|---|---|
| RMSE（反復ごと） | > 2.0 px | M3 と同値（実写収束時実測 0.90〜1.24px） |
| 退化診断 λ3/λ1 | < 0.09 | M2 健全実測 0.269 の 1/3（M3 と同値） |
| 深度レンジ | < 1.4 m | M2 健全実測 4.2m の 1/3（M3 と同値）。檻はシーンが小さいため警告が常時点灯する可能性がある——点灯した場合も合否に使わず、閾値のシーン依存性の実測として記録する |
| 凸包面積比 | < 0.22 | M2 健全実測 0.675 の 1/3（M3 と同値） |

## 7. M4 全体の Go / No-Go（実行前に固定）

- **Go**: パイロットカメラ cam05520125 が baseline で「成立性（§6.1）+ 受理（§6.2）+ 総合判定の前提条件（§6.4）」をすべて満たす
- **No-Go**: 上記を満たさない → 失敗モード（マッチ不足 / 深度不良 / レンダ破綻）を (b-1)〜(b-4) の実測から特定し、roadmap M3 の切り分けフロー（3DGS 再撮影 / マッチャー変更（要・別 criteria lock）/ 手法棄却）へ
- baseline No-Go 時、Stage 1.5 レスキューを適用して**別記録**する（§3。レスキュー成功は Go/No-Go を変えないが、Stage 1.5 正式採用条件の観測事例になる）
- 根拠: パイロット1カメラのため過半数判定は定義できない。単一カメラの成立/不成立をそのまま判定とし、範囲を「パイロット範囲」と明示する（roadmap の固定事項）

## 8. 実験手順の骨子と記録

1. **Stage 0（疎通確認）**: 6点PnP → 初期ポーズでレンダ → 実写との重畳PNG を目視確認（座標系整合の最終確認）。レンダの有効画素率・有効深度の分布（z 下限 0.5m との干渉有無、§4）・SIFT キーポイント数を記録
2. 本実験: §5 の手順でサンプリング実行 → §6 の判定
3. baseline 失敗時のみ: Stage 1.5 レスキューを別記録で実行
4. 判定と (b-1)〜(b-4) の集計
- 進め方: 「各ステップ直前に予測（数値）→実行→照合」方式。記録先 `experiment_log.md`（本ディレクトリ）
- 実験スクリプトは M3 の部品（`pipeline_loop.py`・`m3_run.py`・`m3_1_sampling.py`・`m3_2_pooled.py`・`d3_arbitrate.py`）を流用して作成し、**Codex レビュー収束後に実行**する
- 生データ（npy/npz/png）はコミットしない（`data/` ごと gitignore 済み。結果 txt・スクリプト・ログはコミットする）
