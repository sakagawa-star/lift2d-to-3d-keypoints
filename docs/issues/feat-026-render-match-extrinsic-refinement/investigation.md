### 1.2 原因分析

- **原因箇所**: requirements.md FR-001/FR-002/FR-005 と design.md §4.1/§4.2/§4.5/§4.6 の「6点ちょうど」固定
- **原因の説明**: 「6点」は檻運用（新規シーンで最小限の6点のみをプロットする）のシナリオから一般化した制約であり、病院のように多点の手動データが既に存在する運用を考慮していなかった（根本原因: ヒアリング漏れ。表面的原因ではない）
- **実証実態との照合（変更の妥当性根拠）**: 点数がパイプラインに効く箇所は初期PnPと二峰仲裁の2箇所のみ（Stage 2〜6 の反復は手動点数に無関係）。両箇所とも多点構成の実証実績がある:
  - 初期値: M3/M3b の P0 系列は基準ポーズ（=同じ多点データから作られた全点PnP解）を初期値としてリファイン成立を実証済み
  - 仲裁: D3 は多点手動点による仲裁を実証した。厳密には D3 の実行前固定判定は **M3-0a inlier 名簿の中央値**（`d3_arbitrate.py` 冒頭に明記）であり、**全点中央値も同時に記録され A/B 差 1.311px で同じ採用結果**だった（`d3_result.txt`）。本正式仕様が全点中央値を採用する理由は、外部の inlier 名簿（実験成果物）への依存を避け、**ツールの入力だけで閉じる**ため。6点だけでの仲裁は M4-2 で出番がなく（単峰受理）未実証
  - したがって「6点以上・全点使用」への変更は実証範囲から外れる変更ではなく、病院シーンについては実証済み構成に近づく変更である
