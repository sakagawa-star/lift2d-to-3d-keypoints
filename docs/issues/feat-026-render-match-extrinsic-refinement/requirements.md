# feat-026 要求仕様書: レンダリング＋自動マッチングによるカメラ外部パラメータ精緻化

- 準拠: `docs/REQUIREMENTS_STANDARD.md`
- 状態: draft（Codex 再帰レビュー収束 + 人レビュー前）
- 根拠となる検証: M1〜M4-2 の実測（`roadmap.md` / `findings.md` / `experiments/`）。本仕様の数値定数はすべて criteria lock 下の実験で実証された値であり、出典を各所に付記する
- ユーザー確定仕様（2026-08-02 ヒアリング）: ①実装形態は phase4 + matcher_lab の2環境 subprocess 連携、②マッチャーは LoFTR（outdoor 重み・confidence 閾値 0.2）固定、③出力は Calib_scene.toml 型の新規ファイル、④Stage 1.5（粗整列段）は保留リスト行き（正式採用条件「baseline 失敗→救済成功1件以上」が M3/M4/M3b/M4-2 で未観測のため）

## 1. プロジェクト概要

- **何を作るか**: 3DGS シーン（PLY）と実写画像から、カメラ外部パラメータ（R, t）を自動で精緻化するバッチツール。1カメラあたり**6点以上**の手動プロット（2D-3D 対応点。最少6点）を入力に、レンダ画像と実写画像の自動マッチング（LoFTR）・深度リフト・PnP の反復で外部パラメータを求める
- **なぜ作るか**: 現行の20点方式（手動プロット20点による全点 PnP）は手動作業が多く、プロット誤差がそのまま外部パラメータに乗る。手動作業を最少6点に減らし、自動リファインで外部パラメータを得る（既存の多点 CSV がある場合はそのまま入力でき、全点が使われる）。品質の実績: M3（病院シーン）で20点方式と統計的に不可分（p95 内）の解を確認済み。ただし**本ツールの受理判定は pooled 合意・前提条件・診断値に基づく運用受理であり、真値精度や20点方式超えは主張しない**（独立検証データが確保できていないため。M3 criteria §5.4 / M4 criteria の限定と同一）
- **誰が使うか**: てんかん患者観察研究（映像→3Dキーポイント生成）の解析担当者
- **どこで使うか**: 開発機 gtune2（Linux、RTX 5060 Ti 16GB）。phase4（Python 3.10 / gsplat）と matcher_lab（Python 3.12 / kornia）の2つの uv 環境を subprocess で連携して使う

## 2. 用語定義

機能設計書・コード内でも同じ用語を使う。

| 用語 | 定義 |
|---|---|
| 手動点PnP | 入力された全手動点（一意な 2D-3D 対応、6点以上）から cv2.solvePnPRansac + solvePnP(ITERATIVE) で初期外部パラメータを求める処理 |
| チェーン | 1つの初期値から始まる反復系列。A=無摂動（手動点PnP解）、B/C=手動点PnP解に 5cm/2° の摂動（seed 11/12）を加えた系列の計3本 |
| サンプリング | 各チェーンで k=0 の反復1回の後、k=1 の反復条件で 20 回反復し、各回の解（ポーズ）を収集すること（M3-1 で確立） |
| pooled 合意 | 3チェーン計60サンプルを統合したクラスタ分析。最大クラスタ占有率 f_c と第2クラスタ占有率で単峰/二峰/不受理を判定する（M3-2 で確立） |
| 仲裁 | 二峰時に、入力された全手動点の再投影誤差中央値で2峰のどちらを採用するか決める処理（D3 で多点手動点による仲裁を実証。D3 の固定判定は inlier 名簿中央値だが、全点中央値でも同じ採用結果を確認済み。本仕様が全点を採用するのは外部名簿に依存せず入力だけで閉じるため） |
| 方式A | gsplat 1.5.3 の 3DGUT 経路で歪み付き深度を得る2パスレンダ（z を色として流しαで正規化） |
| ゲート | マッチ点の選別条件。変位・α・z範囲・深度分散・2×2広がりの AND（Stage 4） |
| N | ゲート通過後のマッチ点数。N ≥ 30 が反復成立の条件 |
| 準誤マッチ | ゲートを通過したが RANSAC でインライアにならなかったマッチ |
| K既知 | 内部パラメータ（K・歪み係数）は入力 TOML の値を使い推定しないこと |
| silent failure | 失敗段（マッチ数/ゲート/PnP）を特定できない失敗。本ツールでは禁止 |

## 3. 機能要求一覧

### FR-001 入力検証（Must）

- **概要**: 実行開始時に全入力の整合を検証する。不備は2分類で扱う: **全体停止する入力不備**（ファイル欠落・読込不可、CSV の重複行・欠損列・非有限値（NaN/inf））は処理開始前に明示的エラーで停止し、**カメラ単位の不整合**（画像サイズ不一致、対応点不足（一意6点未満）、2D 座標の画像範囲外）は当該カメラのみ失敗として記録し他カメラの処理を続行する（design §4.1 と同一の分類）
- **入力**: 内部パラメータ TOML（Calib_scene.toml 型。K・歪み係数・画像サイズ）、3D基準点 CSV（kijunten_locations.csv 形式）、2D点 CSV（points_2d.csv 形式）、実写画像（PNG、カメラごとに1枚）、3DGS PLY
- **出力**: 検証結果のログ行（成功/失敗と失敗理由）
- **受け入れ基準**:
  1. 画像サイズが TOML の width/height と不一致の場合、カメラ名と両サイズを明示して**当該カメラを失敗として記録し、他カメラの処理は続行する**（design §4.1 のカメラ単位失敗の扱いと同一。バッチ全体は止めない）
  2. 対象カメラの 2D-3D 対応が「**一意な ObjectName 6個以上**」でない場合、点数を明示して**当該カメラを失敗として記録し続行する**（6個以上あれば全点を使用する）。一意性の定義: 3D CSV は ObjectName が一意、2D CSV は (camera_name, ObjectName) が一意、対応は両者の交差集合。画像範囲外の 2D 座標も当該カメラ失敗として検出する
  3. PLY・TOML・CSV・画像ファイルのいずれかが読めない場合、および CSV に重複行（3D: ObjectName、2D: (camera_name, ObjectName)）・必須列の欠損・非有限値（NaN/inf）がある場合は、ファイルパスと内容を明示して**全体エラーで停止する**（CSV データ自体の破損として扱う）

### FR-002 手動点PnP 初期値算出（Must）

- **概要**: 入力された全手動点（6点以上）から初期外部パラメータを求める（処理は M4 §5-1 と同一。M4/M4-2 は6点、M3 系は多点の初期値で実証済み）
- **入力**: 6点以上の 2D-3D 対応、K・歪み係数
- **出力**: 初期ポーズ（rvec, tvec）、inlier/outlier の点名一覧
- **受け入れ基準**:
  1. cv2.solvePnPRansac（iterationsCount=1000, reprojectionError=8.0, SOLVEPNP_ITERATIVE）→ inlier で solvePnP(ITERATIVE) 精密化の2段で解を返す
  2. RANSAC 失敗または inlier < 4 の場合、明示的エラーで当該カメラを失敗として記録する（他カメラの処理は継続する）
  3. outlier になった点の名前をログに出力する

### FR-003 反復リファイン1回分（Must）

- **概要**: 現在ポーズから Stage 2〜6（レンダ → マッチング → ゲート → 深度リフト → PnP）を1回実行し、更新ポーズを返す。処理・定数・順序は M4-2 の `run_iteration_matcher_m4`（実測根拠）と同一とする
- **入力**: 現在ポーズ、実写画像、PLY、K・歪み係数、反復番号 k
- **出力**: 更新ポーズ、診断値（生マッチ数・変位後・除外内訳・N・inlier 数・RMSE・退化診断3種）
- **受け入れ基準**:
  1. レンダは方式A（near_plane=0.5、distort=True）で色・深度・αを得る
  2. マッチングは matcher_lab 環境の CLI を subprocess で呼ぶ。LoFTR（kornia 0.8.3、outdoor 重み）、入力解像度 1280x720（係数 1.5 で原寸 1920x1080 へ逆写像）、confidence ≥ 0.2 で選別する
  3. マッチ座標の原寸範囲内率が 100% 未満、または逆写像 round-trip 誤差が 0.5px を超えた場合、座標変換の実装欠陥として即エラー終了する
  4. ゲートは M2〜M4-2 と同一の定数・順序（変位 τ_px は引き締めスケジュール、α、z範囲、深度分散、bilinear 2×2広がり）で適用する
  5. ゲート後 N < 30 の場合、失敗段「ゲート生存 N=<値> < 30」を記録して当該反復を失敗とする
  6. 除外内訳は depth_ok → α → z範囲 → 分散の順の逐次分類で記録する

### FR-004 サンプリング型リファイン（Must）

- **概要**: 3チェーン（A/B/C）それぞれで k=0 の反復1回 + k=1 条件の反復20回を実行し、計60サンプルの解を収集する（M3-1/M4 §5-2 と同一手順）
- **入力**: 手動点PnP 初期ポーズ
- **出力**: 60サンプルの解、チェーンごとの成立/失敗と失敗段
- **受け入れ基準**:
  1. チェーン B/C の摂動は 5cm/2°、seed 11/12 の固定値とする
  2. サンプリングの乱数 seed は「基点 + チェーン番号×25 + 反復番号」の規則で固定し、同一入力での再実行が同一結果になる
  3. いずれかの反復が失敗した場合、そのチェーンを失敗とし失敗段を記録する（silent failure 禁止）

### FR-005 合意判定と受理（Must）

- **概要**: 60サンプルの pooled クラスタ分析で最終解を決定する（M3-2/M4 §6.2 と同一判定）
- **入力**: 60サンプルの解、入力された全手動点の 2D-3D 対応（仲裁用）
- **出力**: 受理/不受理、受理形態（単峰高合意/仲裁成立の二峰）、最終解（rvec, tvec）、f_c・第2クラスタ占有率・RMS 半径
- **受け入れ基準**:
  1. 3チェーンすべて成立（60/60 サンプル収集）でない場合は不受理とする
  2. 単峰高合意: f_c ≥ 0.7 かつ第2クラスタ占有率 < 0.2 なら受理し、最大クラスタ内平均を最終解とする
  3. 二峰（第2クラスタ占有率 ≥ 0.2）: 第1+第2 合計占有率 ≥ 0.9 かつ全手動点の再投影誤差中央値の峰間差 ≥ 1.0px の場合のみ受理し、誤差の小さい峰のクラスタ内平均を最終解とする
  4. 上記以外（低合意単峰・仲裁不成立の二峰・多峰）は不受理とし、その分類をログに出力する

### FR-006 前提条件チェックと診断記録（Must）

- **概要**: 受理解の妥当性チェックと診断値の記録（M4 §6.4/§6.5 と同一）
- **入力**: 手動点PnP 初期解、最終解、全反復の診断値
- **出力**: 前提条件の判定、診断レポート
- **受け入れ基準**:
  1. 初期解と最終解の差（カメラ中心距離・回転角）が 50cm または 10° を超えた場合、当該カメラを「前提条件違反」として失敗扱いにする（M2 実測収束域の外）
  2. 診断値（反復ごとの RMSE・λ3/λ1・深度レンジ・凸包面積比・準誤マッチ率）を記録し、暫定警告閾値（RMSE>2.0px、λ3/λ1<0.09、深度レンジ<1.4m、凸包比<0.22）の点灯を警告としてレポートに含める（合否には使わない）
  3. 全手動点の再投影誤差中央値を初期解・最終解の両方で記録する（合否には使わない）

### FR-007 結果出力（Must）

- **概要**: 精緻化済み外部パラメータと診断レポートをファイル出力する
- **入力**: カメラごとの最終解・受理判定・診断値
- **出力**: (a) Calib_scene.toml 型の新規 TOML（**入力 TOML の全カメラを元の順序で含める**。受理した対象カメラのみ rotation/translation を最終解に置換し、不受理・失敗・`--cameras` 対象外のカメラは全キーを入力値のままコピーする。**入力ファイルは変更しない**）、(b) 診断レポート（テキスト。カメラごとの受理形態・f_c・失敗段・警告一覧）
- **受け入れ基準**:
  1. 出力 TOML を既存の下流ツール（phase4/render_keypoints.py の `load_cameras_toml`）が追加改修なしで読めること
  2. 不受理・失敗のカメラは出力 TOML に**入力値（元の rotation/translation）をそのまま残し**、レポートに「未精緻化」と明記する
  3. 出力ファイルが既に存在する場合は上書きせずエラー終了する（明示オプション指定時のみ上書き可）

### FR-008 バッチ処理（Must）

- **概要**: TOML に含まれる複数カメラを一括処理する
- **入力**: 対象カメラ名のリスト（省略時は TOML 内の全カメラのうち、**2D点 CSV に当該カメラ名の行がある全カメラ**。対応点が6点未満のカメラは FR-001 のカメラ単位失敗として記録される。design §4.1 と同一の定義）
- **出力**: カメラごとの結果（FR-007）と全体サマリ（受理 n/全体 m）
- **受け入れ基準**:
  1. 1カメラの失敗が他カメラの処理を止めない
  2. 全体サマリに「受理（単峰）/受理（仲裁）/不受理/失敗（失敗段）」の分類でカメラ数を出力する

### FR-009 マッチャー CLI（Must）

- **概要**: matcher_lab 環境で動く LoFTR 推論 CLI（M3b の `matcher_cli.py` を実測根拠とする正式版）
- **入力**: 画像2枚（原寸 1920x1080）、出力先パス
- **出力**: マッチ座標（原寸座標）・confidence・変換メタ（解像度・逆写像係数・round-trip 誤差・範囲内率）の NPZ
- **受け入れ基準**:
  1. LoFTR outdoor 重みをローカルキャッシュ（`~/.cache/torch/hub/checkpoints/loftr_outdoor.ckpt`）から読み、実行時にネットワークへ接続しない
  2. CUDA OOM は専用終了コード（42）で親プロセスへ通知する
  3. 同一入力での再実行が同一出力（マッチ数・座標とも一致）になる（M3b/M4-2 フェーズ0 実測で決定性を確認済み）

### FR-010 実行ログ（Should）

- **概要**: 反復ごとの診断行（k、マッチ数、N、inlier、RMSE、更新量、警告）を標準出力とログファイルの両方に出す
- **受け入れ基準**: 失敗時にログだけで失敗段（マッチ数/ゲート/PnP/前提条件）が特定できること

## 5. 制約条件

- **使用必須**: phase4 環境（Python 3.10、torch、gsplat 1.5.3、OpenCV、NumPy、tomli）、matcher_lab 環境（Python 3.12、torch、kornia 0.8.3）。2環境は uv 管理で、連携は subprocess + ファイル受け渡し（PNG/NPZ）に限定する
- **レンダ制約**: gsplat 3DGUT 経路は RGB+ED 非対応のため深度は方式A（2パス）で取得する（findings §2）。phase4 の gsplat JIT ビルドには `TORCH_CUDA_ARCH_LIST="9.0+PTX"` が必要（CLAUDE.md 記載の既知制約）
- **K既知モード限定**: 内部パラメータ・歪み係数は入力 TOML の値を使用し推定しない
- **マッチャー固定**: LoFTR（kornia 0.8.3 組み込み、outdoor 重み、入力 1280x720、confidence ≥ 0.2）。この構成のみが M3b/M4-2 で実証済み
- **画像サイズ**: 原寸 1920x1080 のみ対応（M1〜M4-2 の全実証がこのサイズ。他サイズは検証外のためエラーとする）
- **scipy は使用しない**（Stage 6 は cv2 の PnP のみ。ロバスト非線形最小二乗は保留リスト）

## 6. 優先順位（MoSCoW）

- **Must**: FR-001〜FR-009、NFR-001〜NFR-005
- **Should**: FR-010
- **Could**: なし
- **Won't（今回やらない。保留リスト）**: Stage 1.5（粗整列段。採用条件未観測）、MASt3R 切替オプション（同一解精度が基準僅差で不足）、ロバスト非線形最小二乗（Huber/TRF）、退化診断閾値の較正（暫定警告のまま）、1920x1080 以外の画像サイズ対応、内部パラメータの同時推定
- **MVP**: FR-001〜FR-007 による単一カメラ処理（FR-008 のバッチは MVP に含むが、並列化はしない=逐次処理）
