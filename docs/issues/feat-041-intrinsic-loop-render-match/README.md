# feat-041: レンダ＋マッチング反復による内部パラメータ（K・歪み）と外部パラメータの同時推定

## ステータス

Closed（2026-11-25 完了。イテレーション2 の正式判定で合格（median 0.671px、valid_ratio 0.209）、ユーザー手動テスト合格。経緯: 初版（codex-01〜08）→ 実データ不合格（MASt3R の 3.75px 量子化による見かけの収束）→ イテレーション1（i≥1 を LoFTR、codex-09〜13）→ 未収束 → 追加測定 m1 → イテレーション2（収束しきい値 2.0px、未収束時 TOML、合否基準を中央値のみ、--overwrite 廃止、codex-14〜37）。別案件 bug-006 を起票）

## 概要

3DGS（PLY）を作った部屋の中でスマートフォン（Galaxy S25）で撮った静止画について、内部パラメータ（焦点距離・歪み係数）と外部パラメータ（R, t）を推定する。チェッカーボードによる事前キャリブレーションは使わない。手順は次のとおり。

1. 内部パラメータの初期値は Exif から作る（焦点距離は 35mm 換算値から換算、歪みはゼロ、主点は画像中心）
2. 外部パラメータの初期値は手動点（一意 6 点以上）の PnP で求める（`refine_extrinsics.py` の Stage 1 と同じ）
3. 現在のパラメータで 3DGS 内に仮想カメラを置いてレンダリングし（RGB と深度）、実画像との 2D-2D マッチを MASt3R などで求める
4. レンダの深度からマッチ点を 3D に戻し、2D（実画像）-3D の対応を作る
5. 2D-3D 対応から、内部パラメータ（焦点距離・歪み）と外部パラメータをまとめて最小二乗で推定する
6. 3〜5 を内部パラメータが落ち着くまで繰り返す
7. 落ち着いた内部パラメータを固定し、最後に `refine_extrinsics.py`（feat-026）で外部パラメータを精緻化する

## 背景

- 目的: 3DGS を作った部屋で撮った静止画から、撮影したカメラの位置と向きを推定・精緻化する（2026-11-20〜25 の検討）
- スマートフォンは複数の人が使い、ピント位置も写真ごとに変わるため、チェッカーボードで内部パラメータを事前に求める方式は不採用（ユーザー決定）
- `refine_extrinsics.py` は内部パラメータが既知であることを前提にしており、内部パラメータは推定しない（feat-026 では「内部パラメータの同時推定」を Won't としていた）
- 通常の写真の Exif には歪み係数が入っていない。焦点距離の 35mm 換算値は整数に丸められている

## 決定済みの事項（2026-11-20〜25 の検討で確定）

| 項目 | 決定 |
|---|---|
| 撮影端末 | Galaxy S25（無印）、One UI 7.0、メインカメラ（1x）。写真は 4000x3000（4:3） |
| 画像サイズ | 中央で 16:9 に切り抜き（4000x2250、原本の y=375〜2624）、1920x1080 に INTER_AREA で縮小した画像を使う（A案。既存の `refine_extrinsics.py` / `loftr_cli.py` / `mast3r_cli.py` が 1920x1080 固定のため）。4:3 のまま使う対応（B案）は本案件の範囲外 |
| 撮影時の縦横比 | 4:3（既定のまま）で撮り、切り抜きは前処理で行う。撮影者の操作ミス（縦横比の設定違い）を後処理で吸収するため |
| 内部パラメータの初期値 | Exif 由来。fx = fy = 35mm換算焦点距離 × 画像対角[px]/43.27 × 縮小率、主点は (W/2, H/2)、歪みはゼロ |
| ループで使うマッチャー | MASt3R など（視点・拡大率の差に強いもの） |
| 最終の外部パラメータ精緻化 | `refine_extrinsics.py`（LoFTR）を使う |
| 検証の基準 | S25 で撮影した写真だけを基準とする（ユーザー決定 2026-11-25）。3DGS に写り込んだ S25 本体の位置は合否判定に使わない（Blender で点を置く誤差を含み、推定と同じ 3DGS 由来で、向きは 1〜2° 程度の精度でしか求まらないため、真値と呼べない） |

## 現状調査メモ

### 疎通確認（既存ツールのみ、2026-11-25）

- 入力: `phase4/data/10F/`（PLY `point_cloud.ply`、写真 `s25_original/20261124_152436.jpg`、前処理後 `s25_images/s25_20261124_152436.png`、初期TOML `s25_intrinsic_init.toml`（fx=fy=1275.7、主点 (960,540)、歪みゼロ））、基準点 `phase0/data/kijunten_locations_10F.csv` / `phase0/data/points_2d_10F.csv`（原本座標。1920x1080 換算は `phase4/data/10F/points_2d_10F_1920x1080.csv`）
- PLY: PortalCam 製、1,544,038 ガウシアン、SH 0次のみ、Z-up・メートル単位（1〜99% 点で 6.9m × 4.8m × 2.9m）
- 手動点 6 点、Exif の K・歪みゼロでの PnP: RMSE 3.36px、最大 5.42px
- `refine_extrinsics.py` の結果: 受理（単峰）。手動点 6/6 採用。k=1 の RMSE 1.08〜1.29px（PnP 外れ値しきい値 2px の inlier のみで計算）、inlier 率は k=0 の約 79%（8px）から k=1 の約 57%（2px）に低下。3 チェーン合意 3.04mm / 0.052°。初期解→最終解 4.68cm / 0.884°。全反復で `vol_ratio<0.09` 警告
- 推定カメラ位置 (-0.558, 1.536, 0.365)。ユーザーが Blender 上で 3DGS に写った S25 と比較し、位置がずれていることを確認した。ユーザーは歪み係数をゼロにしたことが原因と見ている

## ヒアリングで確定した要件

2026-11-25 ヒアリング:

| 項目 | 決定 |
|---|---|
| 推定する歪みモデル | k1, k2 のみ（p1, p2 は 0 に固定。`estimate_camera_params.py --zero-tangent` と同じ） |
| 主点 (cx, cy) | 推定する（初期値は画像中心 (960, 540)） |
| 実行の形 | 1 コマンドで最後まで実行する。新スクリプトがループを回し、収束した内部パラメータの TOML を作ってから `refine_extrinsics.py` を自動で呼ぶ |
| 検証の方法 | S25 の写真（前処理後 1920x1080）と、推定した最終パラメータ（K・歪み・R, t）でレンダした画像を重ね合わせて比較する。ずれは OpenCV の DIS オプティカルフロー（推定に使う MASt3R・LoFTR とは独立）で画素ごとに求め、3DGS が再現できている画素（α > 0.5 かつ深度 0.5〜10m）で集計する。半透明合成・市松模様合成・ずれのヒートマップも出力して目視確認に使う |
| 検証の合格ライン | ずれの大きさの中央値 ≤ 1px かつ 95 パーセンタイル値 ≤ 3px（1920x1080 の画素単位）。2026-11-25 にいったん「3DGS 上の S25 のレンズ位置との差 5cm 以内」としたが、上記の重ね合わせ方式に置き換えた |
