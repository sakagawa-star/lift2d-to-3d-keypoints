# feat-041 要求仕様書: レンダ＋マッチング反復による内部パラメータ（K・歪み）と外部パラメータの同時推定

## 1. プロジェクト概要

### 1.1 何を作るのか

3DGS（PLY）を作った部屋の中でスマートフォンを使って撮った静止画1枚から、そのカメラの内部パラメータ（焦点距離・主点・放射歪み k1, k2）と外部パラメータ（回転・並進）を推定するツール群を作る。

ツール群は次の3本のスクリプトで構成する。

| スクリプト | 役割 |
|---|---|
| `phase4/prepare_phone_photo.py` | 写真の前処理（切り抜き・縮小）、Exif からの初期内部パラメータ TOML の作成、2D 点の座標変換 |
| `phase4/estimate_intrinsics_loop.py` | 反復ループ（レンダ → マッチング（i = 0 は MASt3R、i ≥ 1 は LoFTR）→ 深度で 3D 化 → 内部・外部パラメータの同時最小二乗）を内部パラメータが収束するまで回し、最後に `phase4/refine_extrinsics.py`（feat-026）で外部パラメータを精緻化し、重ね合わせ評価まで行う |
| `phase4/evaluate_overlay.py` | 写真と、推定パラメータでレンダした画像の重ね合わせ評価（オプティカルフローによるずれの数値化と画像出力） |

### 1.2 なぜ作るのか

- `phase4/refine_extrinsics.py`（feat-026）は内部パラメータが既知であることを前提とし、内部パラメータを推定しない
- スマートフォンは複数の人が使い、ピント位置も写真ごとに変わるため、チェッカーボードで内部パラメータを事前に求める運用は現実的でない（ユーザー決定 2026-11-25）
- 通常の写真の Exif には歪み係数が無く、35mm 換算焦点距離は整数に丸められている
- Exif の焦点距離・歪みゼロのまま `refine_extrinsics.py` を通した疎通確認（2026-11-25、案件 README 参照）では受理されたが、ユーザーが推定位置のずれを確認した

### 1.3 誰が使うのか

本プロジェクトの開発者・研究者（コマンドラインで Python スクリプトを実行できる人）。写真の撮影者は別人でもよい。

### 1.4 どこで使うのか

マシン gtune2（Ubuntu、RTX 5060 Ti、CUDA）。phase4 の uv 環境（gsplat）と matcher_lab の uv 環境（MASt3R、LoFTR）を使う。

## 2. 用語定義

本書・機能設計書・コード内で同じ用語を使う。

| 用語 | 定義 |
|---|---|
| 原本 | スマートフォンで撮影したままの JPEG 画像（例: 4000x3000） |
| 前処理後画像 | 原本を中央で 16:9 に切り抜き、1920x1080 に縮小した PNG 画像 |
| 内部パラメータ | 焦点距離 f[px]（fx = fy = f）、主点 (cx, cy)[px]、放射歪み係数 k1, k2。接線歪み p1, p2 は 0 に固定 |
| 外部パラメータ | OpenCV 規約の world-to-camera の回転（Rodrigues ベクトル rvec）と並進 tvec |
| 手動点 | 人が写真上でプロットした基準点の 2D 座標と、3DGS 座標系での 3D 座標の組（ObjectName で対応付け） |
| レンダ画像 | 現在のパラメータ（内部・外部・歪み）で 3DGS をレンダリングした画像（RGB、深度、α） |
| マッチ | 前処理後画像とレンダ画像の間の 2D-2D 対応点（反復 i = 0 は MASt3R、i ≥ 1 は LoFTR が出力） |
| 深度リフト | レンダ画像側のマッチ点を、レンダの深度とレンダに使ったパラメータで 3DGS 座標系の 3D 点に戻すこと |
| 反復 | 「レンダ → マッチ → ゲート → 深度リフト → 外れ値除去 → 同時最小二乗」の1回分 |
| 内部パラメータ変化量 Δ_intr | 反復の前後の内部パラメータで、画像上の 5x5 格子点が移動する量の最大値 [px]（定義は機能設計書） |
| 収束 | Δ_intr が収束しきい値を下回ること |
| 重ね合わせ評価 | 前処理後画像と最終パラメータでのレンダ画像の画素ごとのずれを DIS オプティカルフローで求め、統計値で合否を判定すること |
| DIS | OpenCV の Dense Inverse Search オプティカルフロー（`cv2.DISOpticalFlow`） |

## 3. 機能要求一覧

### FR-001 写真の前処理と初期内部パラメータ TOML の作成（`prepare_phone_photo.py`）

- **概要**: 原本1枚を前処理後画像に変換し、Exif から初期内部パラメータの TOML を作り、原本座標で打った 2D 点 CSV を前処理後画像の座標に変換する
- **入力**: 原本 JPEG のパス、カメラ名、出力先（画像ディレクトリ・TOML・2D 点 CSV）、原本座標の 2D 点 CSV（`points_2d.csv` 形式）、任意で期待する機種名と期待する実焦点距離[mm]
- **出力**: `{画像ディレクトリ}/{カメラ名}.png`（1920x1080）、初期 TOML（Calib_scene.toml 形式、1カメラ分）、変換後の 2D 点 CSV（当該カメラの行のみ）
- **受け入れ基準**:
  1. 4000x3000 の原本から、原本の y=375〜2624 の範囲を切り出して 1920x1080 に縮小した PNG が出力される
  2. 4000x2252 の原本（16:9 設定で撮影したもの）から、y=1〜2250 の範囲を切り出して 1920x1080 に縮小した PNG が出力される
  3. 初期 TOML の焦点距離は「35mm 換算焦点距離 × 原本の対角画素数 / 43.27 × 1920 / 原本の幅」、主点は (960.0, 540.0)、歪みは [0.0, 0.0, 0.0, 0.0]、rotation / translation は [0.0, 0.0, 0.0]
  4. 2D 点は、原本の座標 (X, Y) を画素中心規約で前処理後画像の座標に変換して出力される（式は機能設計書）
  5. 次の場合は終了コード 1 でエラー終了し、ファイルを出力しない: Exif の `Orientation` が 1 以外、原本が縦長（幅 ≤ 高さ）、高さが幅×9/16 未満、`FocalLengthIn35mmFilm` が無い、`DigitalZoomRatio` が 1.0 以外、期待機種名の指定があり `Model` が一致しない、期待実焦点距離の指定があり `FocalLength` との差が 0.05mm を超える、変換後に切り抜き範囲内に残る 2D 点が一意な ObjectName で 6 個未満
  6. 切り抜き範囲外の 2D 点は出力 CSV から除き、除いた ObjectName を標準出力に表示する

### FR-002 初期外部パラメータの推定（`estimate_intrinsics_loop.py`）

- **概要**: 初期 TOML の内部パラメータと手動点（一意 6 点以上）から PnP で初期外部パラメータを求める
- **入力**: 初期 TOML、カメラ名、3D 基準点 CSV、2D 点 CSV（前処理後座標）、前処理後画像
- **出力**: 初期 rvec, tvec（メモリ上）、レポートへの記録（手動点数、inlier 数、再投影誤差の中央値）
- **受け入れ基準**:
  1. `refine_extrinsics.py` の `pnp_manual` と同じ処理（solvePnPRansac 再投影しきい値 8px → inlier で solvePnP 精密化）で求める
  2. 手動点が一意 6 個未満、または PnP が失敗した場合は終了コード 1 でエラー終了する

### FR-003 反復の1回分（レンダ・マッチ・ゲート・深度リフト・外れ値除去）

- **概要**: 現在の内部・外部パラメータで 3DGS をレンダし、前処理後画像とのマッチ（i = 0 は MASt3R、i ≥ 1 は LoFTR）から 2D-3D 対応を作り、外れ値を除く
- **入力**: 3DGS、前処理後画像、現在のパラメータ、反復番号 i
- **出力**: 外れ値除去後の 2D-3D 対応（前処理後画像の座標と 3DGS 座標系の 3D 点）
- **受け入れ基準**:
  1. レンダは歪みモデル込み（gsplat 3DGUT 経路）で行う
  2. マッチは、反復 i = 0 では `matcher_lab/mast3r_cli.py` を subprocess で呼んで得る。終了コード 42（CUDA OOM）の場合は `--resolution 1280x720` で1回だけ再試行する。反復 i ≥ 1 では、`matcher_lab/loftr_cli.py` を `refine_extrinsics.py` の `call_matcher` 経由で呼んで得る。信頼度が `refine_extrinsics.py` の `LOFTR_CONF_TH` 未満のマッチは使わない。LoFTR の終了コード 42（CUDA OOM）は再試行せず、その反復の失敗とする（`loftr_cli.py` に解像度を変えるオプションが無いため）（investigation.md イテレーション1）
  3. ゲート（変位しきい値、深度の有効性、α、深度範囲、深度分散）は `refine_extrinsics.py` と同じ判定関数・定数で行う。変位しきい値は反復番号で切り替える（値は機能設計書）
  4. 深度リフトは、レンダに使った内部・歪み・外部パラメータで行う。逆歪み変換は反復 100 回・精度 1e-10 で解き、再投影との差が 0.01px を超える点は除く
  5. 外れ値除去は solvePnPRansac で行い、そのしきい値は反復番号で切り替える（値は機能設計書）
  6. 外れ値除去後の対応点数が N_MIN_INTR（機能設計書）未満なら、その反復を失敗として処理全体を終了コード 3 で終了する

### FR-004 内部・外部パラメータの同時最小二乗

- **概要**: 外れ値除去後の 2D-3D 対応から、f、cx、cy、k1、k2、rvec、tvec の 11 変数を同時に最小二乗推定する
- **入力**: FR-003 の 2D-3D 対応、現在のパラメータ（初期値）
- **出力**: 更新後の 11 変数
- **受け入れ基準**:
  1. 再投影残差（`cv2.projectPoints` の結果と前処理後画像の座標の差）を最小化する
  2. 外れ値に頑健な損失関数（soft_l1）を使う
  3. p1, p2 は 0 に固定し、fx = fy = f とする
  4. 合成データ（既知の f, cx, cy, k1, k2, rvec, tvec で投影した点に標準偏差 0.3px のノイズを加えたもの）で、f の相対誤差 0.5% 以内、cx, cy の誤差 3px 以内、k1, k2 の誤差 0.02 以内に推定できる

### FR-005 収束判定と範囲チェック

- **概要**: 反復ごとに内部パラメータ変化量 Δ_intr を計算して収束を判定し、推定値の範囲をチェックする
- **入力**: 反復前後の内部パラメータ
- **出力**: 継続 / 収束 / 失敗の判定
- **受け入れ基準**:
  1. Δ_intr が収束しきい値（機能設計書）未満になった反復で収束とし、ループを終える。ただし、収束と判定してよいのは LoFTR でマッチを求めた反復（i ≥ 1）だけとする。i = 0（MASt3R）では Δ_intr がしきい値未満でも収束とせず、次の反復に進む（MASt3R の座標の刻みによる見かけの収束を防ぐため。investigation.md イテレーション1）
  2. 反復回数の上限（機能設計書）に達しても収束しない場合は、最後の反復の値でループ結果 TOML を書き出したうえで、終了コード 3 で終了する（書き込み自体の失敗の扱いは収束時と同じで、特別な扱いはしない）（`refine_extrinsics.py` と重ね合わせ評価は行わない。investigation.md イテレーション2）
  3. 更新後の値が次の範囲を外れた場合は、終了コード 3 で終了する: f が 0.3×1920〜3.0×1920、|cx − 960| ≤ 192、|cy − 540| ≤ 108、|k1| ≤ 1.0、|k2| ≤ 1.0

### FR-006 外部パラメータの最終精緻化

- **概要**: 収束した内部パラメータを書いた TOML を作り、`refine_extrinsics.py` を subprocess で呼んで外部パラメータを精緻化する
- **入力**: 収束後のパラメータ、FR-002 と同じ手動点・画像・PLY
- **出力**: ループ結果 TOML、`refine_extrinsics.py` の出力 TOML（最終 TOML）と診断レポート
- **受け入れ基準**:
  1. ループ結果 TOML は Calib_scene.toml 形式で、matrix = [[f,0,cx],[0,f,cy],[0,0,1]]、distortions = [k1, k2, 0.0, 0.0]、rotation / translation は最後の反復の値
  2. `refine_extrinsics.py` は `--cameras {カメラ名}` を付けて呼ぶ
  3. `refine_extrinsics.py` が当該カメラを受理しなかった場合は、終了コード 4 で終了する
  4. `refine_extrinsics.py` を呼ぶ前に、収束後の K・歪みで `refine_extrinsics.py` の逆歪み変換（既定の `cv2.undistortPoints`）の誤差を画像全体の格子点で計算し、0.1px を超える場合は呼ばずに終了コード 3 で終了する

### FR-007 実行レポート

- **概要**: 反復ごとの経過と最終結果をテキストのレポートに書く
- **出力**: `{出力ディレクトリ}/{カメラ名}_loop_report.txt`
- **受け入れ基準**: 反復ごとに、マッチ数、ゲート通過数、外れ値除去後の点数、再投影 RMSE、f、cx、cy、k1、k2、Δ_intr、格子被覆セル数（機能設計書）、その反復の所要時間[s]が1行で記録される。`refine_extrinsics.py` と重ね合わせ評価の所要時間[s]も、それぞれを実行した場合に記録される。最後に終了状態（成功・未収束・範囲外・ループ失敗・精緻化不受理・エラー。各終了状態と終了コードの対応は機能設計書）が記録される。重ね合わせ評価を実行した場合は、その結果も記録される。未収束の場合は、ループ結果 TOML を最後の反復の値で書き出したことも記録される。ただし、ファイルの書き込み自体が失敗して異常終了した場合（ディスク容量不足など。終了コード 1）は例外とする: ループ結果 TOML・評価ファイルなどレポート以外の書き込み失敗ではレポートは作成されず、それまでに書かれた成果物（ループ結果 TOML、最終 TOML など）が一部残り得る。レポート自体の書き込み失敗では不完全なレポートが残り得る（機能設計書）

### FR-008 重ね合わせ評価（`evaluate_overlay.py`）

- **概要**: 前処理後画像と、指定 TOML のパラメータでレンダした画像のずれを数値化し、合否を判定し、確認用画像を出力する
- **入力**: TOML、カメラ名、PLY、前処理後画像、出力先のファイル名接頭辞
- **出力**: `{接頭辞}.txt`（統計値と判定）、`{接頭辞}_blend.png`（50% 半透明合成）、`{接頭辞}_checker.png`（市松模様合成）、`{接頭辞}_flowmag.png`（ずれの大きさのヒートマップ）
- **受け入れ基準**:
  1. ずれは DIS で求める。集計対象は、3DGS が再現できており（α > 0.5 かつ深度 0.5〜10m）、写真にテクスチャがあり、順方向・逆方向のフローが整合する画素に限る（条件の値は機能設計書）
  2. 集計対象の画素の割合が全画素の 10% 未満の場合は「判定不能」とする
  3. 集計対象の画素の割合が 10% 以上の場合に、ずれの大きさの中央値 ≤ 1.0px のとき「合格」、それ以外は「不合格」と判定する（10% 未満は基準 2 の「判定不能」が優先する）。95 パーセンタイル値は記録するが、判定には使わない（10F の測定で、95 パーセンタイル値を押し上げるずれ（> 3px）は最下段に集まり、240x180 のセルの中では向きがそろう（一貫性 C の中央値 0.81）が、主点から見た放射成分の符号はセルごとに正 4・負 4 で、隣のセルで反転した。原因は未特定で、仮説は 3DGS の下側の撮影不足による局所的な再現誤差。investigation.md イテレーション2、ユーザー決定）
  4. 画像を一様に 2px 平行移動させたテクスチャ画像の組で、中央値が 1.8〜2.2px になる
  5. `estimate_intrinsics_loop.py` は最終 TOML に対してこの評価を自動で実行する（接頭辞は `{出力ディレクトリ}/{カメラ名}_eval`）。単体の CLI としても実行できる

## 4. 非機能要求

- **NFR-001 処理時間**: 1枚の写真について、`estimate_intrinsics_loop.py` の全体（ループ + `refine_extrinsics.py` + 評価）が 60 分以内に終わる（疎通確認での `refine_extrinsics.py` の所要時間は未計測のため、実データ検証時に各段の所要時間をレポートに記録して確認する）
- **NFR-002 対応環境**: Ubuntu、NVIDIA GPU（CUDA）必須。`TORCH_CUDA_ARCH_LIST="9.0+PTX"` を設定して phase4 の uv 環境で実行する
- **NFR-003 再現性**: 同じ入力で再実行したとき、ループの各反復の推定値が同じになる（`cv2.setRNGSeed` で RANSAC の乱数を固定する）
- **NFR-004 データ保全**: 出力先に同名ファイルがある場合、`--overwrite` が無ければ処理を始める前にエラー終了する（終了コード 1）。ただし `estimate_intrinsics_loop.py` は `--overwrite` を持たない。出力ファイル一式（機能設計書）のいずれかが出力先に存在すれば（リンク先の無いシンボリックリンクを含む）、処理を始める前にエラー終了する（終了コード 1）。再実行するときは、新しい出力先を指定するか、利用者が前回の出力を手で削除する。今回の実行が途中で終わったときに前回の結果と混在しないようにするため（investigation.md イテレーション2）。bug-006 の修正までの運用条件: `--out-dir` には、実行前に存在しない新規のディレクトリ（入力ファイルを含まない）を指定する（最終精緻化の一時ファイル `{camera}_final.toml.tmp` が、残っていたリンク経由で入力を上書きし得るため）。原本・入力ファイルは変更しない
- **NFR-005 オフライン動作**: MASt3R・LoFTR の重みはローカルのものだけを使い、ネットワークからダウンロードしない（既存 CLI の挙動のまま）

## 5. 制約条件

- **画像サイズ**: 前処理後画像は 1920x1080 のみ。`mast3r_cli.py`、`loftr_cli.py`、`refine_extrinsics.py` が 1920x1080 固定のため。原本 4:3 のまま扱う対応はしない
- **使用ライブラリ**: 既存の依存だけを使う（phase4: torch、gsplat、numpy、opencv-python、scipy、Pillow、tomli。matcher_lab: MASt3R、LoFTR（kornia））。新規ライブラリは追加しない
- **既存コードの変更禁止**: `refine_extrinsics.py`、`mast3r_cli.py`、`loftr_cli.py`、`render_keypoints.py`、`render.py` は変更しない（関数・定数を import して使う）
- **1回の実行で扱う写真**: 1枚（1カメラ）
- **同時実行**: 同じ `--out-dir`・カメラ名で `estimate_intrinsics_loop.py` を実行する場合は、前の実行が終了してから起動する（同時実行の排他は行わない。investigation.md イテレーション2）
- **GPU メモリ**: 3DGS（約 150 万ガウシアン）を親プロセスで GPU に保持したまま、MASt3R・LoFTR を別プロセスで実行する（feat-035 と同じ構成）
