## 方針

- CLAUDE.md の開発方針「小さく作って動作確認し、次へ進む」に従い、実装（フロー ステップ6）を8ステップに分割する
- **リスクの高い前提を先に検証する**: 案Aの最大のリスクは「広基線カメラペアで MASt3R のマッチが十分に取れるか」。これを Step 2 の Go/No-Go で早期に確認し、不成立なら BA を作り込む前に方針を見直す
- 各ステップで「実装内容 / 検証方法 / 完了条件 / 失敗時の扱い」を定義する。役割分担は CLAUDE.md「実装の実行方法」に従う: **Sonnet サブエージェントが実装と必須検証（`uv run pytest -v` 全件実行、`tests/results/feat-035_test_result.txt` への保存、ステップに定義された動作確認）まで実施**し、Claude Code 本体が結果確認・追加の実データ確認（GPU実行・測定）・ユーザー報告を行う。コード変更を含む各ステップ（Step 1〜6 と Step 7 の定数反映）の完了条件に「pytest 全件通過と結果ファイル保存」を含める
- **数値判定を伴う検証**（Step 2, 3, 3F, 7）は CLAUDE.md 実験プロトコルに従い、実行前に criteria 文書（測定ゴール）を作成して Codex レビュー（criteria lock）を経る
- 各ステップ完了時にユーザーへ報告し、**承認を得てから次ステップに進む**

## Step 1: MASt3R CLI

- **実装**: `matcher_lab/mast3r_cli.py`（design §2.1。m3b matcher_cli.py の mast3r 経路を移植、`--resolution` 追加）
- **検証**: 近接ペア（cam05520125.png × cam05520126.png）と対面に近いペア（cam05520125.png × cam41520557.png）の2組で実行し、終了コード0・NPZ生成・座標が原寸範囲内・meta の roundtrip 誤差を確認する
- **完了条件**: 2組とも正常終了し NPZ が読める（マッチ数の多寡はここでは問わない。Step 2 の対象）
- **失敗時**: MASt3R 環境の疎通問題として matcher_lab 側を調査（実装には進まない）

## Step 2: 28ペアマッチ数測定と連結性判定（Go/No-Go）

- **実装**: 本体スクリプトの骨格 + `run_pair_matching`（design §2.2。Stage P のみ動く状態）
- **事前作業**: `experiments/p0_pair_connectivity/criteria.md` を作成し Codex レビュー（criteria lock）。定義する問い: (1) 各ペアのマッチ数の分布、(2) N_PAIR_MIN=50 での採用ペア集合が8台を1つの連結成分にするか、(3) しない場合、何台が連結成分に入るか・N_PAIR_MIN をいくつまで下げれば連結するか
- **検証**: 実写8枚で28ペアを実行し、マッチ数一覧と連結性を測定・記録する
- **Go 条件**: cam05520125/126 を含む連結成分に8台全てが入る（N_PAIR_MIN=50 で連結しない場合、連結に必要な値まで下げた**暫定値**での連結を Go とする）
- **注意**: Step 2 は接続可能性の事前計測であり、ここでの N_PAIR_MIN 変更は暫定扱いに限る。最終採用値は Step 7（FR-008）の criteria に基づく実験で決定する（実験プロトコルとの整合）
- **No-Go 時**: 連結しないカメラの扱いをユーザーと協議する。選択肢: (a) N_PAIR_MIN 引き下げ + 品質リスク受容、(b) 連結成分内のカメラのみで先へ進む（対象縮小）、(c) グローバル初期化（MASt3R-SfM/VGGT。prior_work.md §3）の検討として要求仕様に差し戻す。**BA 実装（Step 5）には進まない**

## Step 3: ブートストラップ【完了・主経路外に降格】

- 実施記録: criteria lock（codex-13〜16）→ 実装 → 実測（2026-08-17/18）。定量ゲートは通過したが、**目視確認でユーザーが cam41520554 の鏡映誤配置を発見（NG）**。追加診断で全6台がマッチ相手カメラの位置に誤収束していること、原因が対称環境での MASt3R 偽マッチであることを特定（`experiments/p0_bootstrap/experiment_log.md`）
- 帰結（案A採用。2026-08-18）: Stage B は主経路から除外（コード・テストは温存）。初期ポーズは Step 3M の手動経路で全台確定する

## Step 3R: 各カメラの反復精緻化【廃止（案A）】

- 案Aにより全カメラが feat-026 精緻化済みの信頼初期カメラとなるため廃止。経緯は requirements FR-009【廃止】参照

## Step 3M: 手動プロット + feat-026 による残り6台の確定（ユーザー作業を含む）

- **ユーザー作業**: 残り6台（cam05520128, cam05520129, cam41520554, cam41520556, cam41520557, cam41520558）について、手動 2D 基準点（各カメラ一意6点以上）を `points_2d_inuyama.csv` に追記する（3D側は既存の `kijunten_locations_inuyama.csv` を使用。クリック精度は粗くてよい: feat-026 の受理前提は初期解から 50cm/10° 以内）
- **実行**（本体）: `refine_extrinsics.py` を8台対象で実行し、全台受理の TOML を得る（既存2台は再実行でも既存結果の流用でもよい。出力例: `cage_refined_all8.toml`）
- **検証**: 各カメラの受理判定（単峰合意）と、レンダ vs 実写ずれ中央値（feat-026 調査で確立した測定法、near_plane=0.25）を記録する
- **ユーザー確認**: 8台分のレンダ vs 実写比較画像の目視（固定構造の輪郭が二重像にならず重なること。金網などの薄構造・至近・グレージング角は判定対象外）。**推定位置の妥当性（物理的な設置位置と矛盾しないか）も確認いただく**（今回の教訓）
- **失敗時**: 不受理カメラはクリックの見直し・点数追加で再試行。解決しない場合は協議

## Step 3F: エピポーラ整合フィルタ（Stage F）

- **実装**: `filter_cross_matches`（design §2.45）+ 単体テスト。Stage B 呼び出しの主経路からの除去と `--init-cameras` 全カメラ必須チェックも同時に実装する
- **事前作業**: `experiments/p0_epi_filter/criteria.md` を作成し criteria lock。内容: 測定項目（28ペアのフィルタ前後の対応点数・生存率の分布。EPI_TOL_PX=3.0 は暫定値）に加え、**Go 条件として「フィルタ後採用ペアグラフで全ポーズ確定カメラが単一連結成分に入ること」を事前定義**し、直前予測枠に採用ペア数・連結成否の予測を含める
- **検証**: 8台の確定ポーズ（Step 3M の TOML）でフィルタを実行し、ペア別生存統計を記録する。対称偽マッチが支配的なペア（生存率が著しく低いペア）の分布を確認する
- **完了条件**: pytest 全件通過・結果保存。フィルタ後の採用ペアグラフで**全ポーズ確定カメラが単一連結成分**に入ること
- **失敗時（事前定義）**: 連結性不成立（全ペア不採用を含む）の場合は次の選択肢をユーザーと協議する: (a) 連結成分内のカメラのみで対象縮小、(b) EPI_TOL_PX の再検討（criteria 改訂・再lockを経て再実行）、(c) 方針の差し戻し。協議までBA実装以降に進まない

## Step 4: アンカー対応点取得

- **実装**: `collect_anchor_points`（design §2.4）
- **検証**: ポーズ確定カメラ（8台）の N_A 一覧を出力し、N_A ≥ 30（BA参加条件）の成立状況を確認する。cam05520125/126 は feat-026 実績（数千点）と同水準であることを確認する
- **完了条件**: BA 参加カメラが2台以上
- **失敗時**: アンカー不足カメラが多数の場合は原因（レンダ品質・LoFTR失敗）を調査して報告する

## Step 5: バンドル調整

- **実装**: `build_ba_problem` + `run_bundle_adjustment`（design §2.5。三角測量・交会角重み・疎ヤコビアン・NaNバリア含む）
- **検証**:
  - 単体テスト（合成データ）: 既知の8ポーズ+3D点から生成した観測に摂動を与え、BA が復元することを pytest で確認（tests/test_feat035_multiview.py の該当分）
  - 実データ: 収束（status≥1）、アンカー/クロス残差が初期値から低下（以上が完了条件。requirements FR-005 の受け入れ基準と同一）。**非悪化フォールバック**の動作確認（BA前後のアンカー残差比較がレポートに出力され、悪化 >0.3px のカメラが BA 前ポーズに戻ること。単体テストで固定）。ポーズ変化量（cm/度）は**参考診断値**として記録のみ行う（requirements/design に受け入れ条件として存在しないため、ブロッキング条件にしない。異常に大きい場合は報告して判断を仰ぐ）
- **失敗時**: 収束しない・残差が悪化する場合は design §2.5 の見直しに差し戻す（実装で回避しない）

## Step 6: 評価・レポート・TOML出力（MVP完成）

- **実装**: `evaluate_holdout` + `write_multiview_toml` + レポート + CLI 統合（design §2.6/2.7）
- **検証**: `uv run pytest -v` 全件（結果を `tests/results/feat-035_test_result.txt` に保存）。実データで end-to-end 実行し、レポート (a)〜(i) 全項目の出力と、出力TOMLの `render_keypoints.py` 読込レンダ成功を確認する
- **ユーザー確認**: フロー ステップ7（手動テスト）。出力TOMLに含まれる**ポーズ確定カメラ分**のレンダ vs 実写の比較・除外カメラ一覧・レポートを提示する（8台比較は代替経路を含め全台確定した場合のみ）
- **失敗時**: 不具合は BUGFIX_STANDARD に従い investigation.md へ記録し、承認を得てステップ2〜7（フロー）を繰り返す

## Step 7: パラメータ決定実験（FR-008）

- **事前作業**: `experiments/p1_param_sweep/criteria.md`（design §3 の内容: 走査範囲・記録項目・採用値の決め方）を作成し criteria lock
- **実施**: N_PAIR_MIN・HUBER_PX・W_CROSS/W_ANCHOR・HOLDOUT_RATIO・THETA_SIGMA_DEG（w=1 含む）・EPI_TOL_PX の走査。任意項目（アンカー MASt3R 比較）の採否は criteria 作成時に決める
- **ユーザー確認**: 採用値の承認。承認後、本体の定数を採用値に更新する（コード変更は Sonnet 委任）
- **反映後の再検証**: 定数更新後に `uv run pytest -v` を再実行して `tests/results/feat-035_test_result.txt` を更新し、採用パラメータで end-to-end（レポート (a)〜(i) 出力・出力TOMLの `render_keypoints.py` 読込レンダ）を再確認する
- **最終手動テスト**: 反映後の再検証結果（出力TOMLに含まれるポーズ確定カメラ分のレンダ vs 実写比較・除外カメラ一覧・最終レポート）をユーザーに提示し、フロー ステップ7 の手動テストとして最終確認いただく。問題があれば BUGFIX_STANDARD に従い investigation.md へ記録し、承認を得て修正サイクルを回す。**Step 8（完了処理）は最終手動テストの合格後にのみ進む**
