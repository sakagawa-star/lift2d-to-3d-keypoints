# feat-035 要求仕様書: 8台多視点同時外部パラメータ調整（MASt3Rクロスカメラ + 3DGSアンカー）

作成日: 2026-08-17 / ステータス: Draft（Codexレビュー前）

## 1.1 プロジェクト概要

- **何を作るのか**: 同時撮影した8台のカメラの外部パラメータ（R, t）を、3DGSモデルへのアンカー対応点とカメラ間クロスマッチング対応点の再投影誤差を同時最小化して一括調整するバッチスクリプト、およびそれに必要な MASt3R ペアマッチング CLI を作る。
- **なぜ作るのか**: feat-026 の単体精緻化は各カメラを独立に3DGSへ合わせるため、カメラ間の相互整合性（三角測量の品質）は間接的にしか保証されない。また現状は手動基準点があるカメラ（2台）しか精緻化できない。手動基準点は精度が悪く今後さらに悪化する前提のため、当初は手動基準点を使わない自動初期化（クロスマッチによるブートストラップ）を計画した。**改訂（2026-08-18 案A採用）**: ほぼ対称なケージ環境では広基線クロスマッチが対称構造の偽マッチで破綻し、自動初期化の全6台が誤った位置（マッチ相手カメラの位置）に収束することが実測で判明した（`experiments/p0_bootstrap/experiment_log.md` 追加診断）。このため初期ポーズは**全カメラを手動プロット + `refine_extrinsics.py`（feat-026）で確定**する方針に変更し、本案件の中心価値を「エピポーラ整合フィルタ済みクロス対応点による多視点同時BA（相互整合性の仕上げ。非悪化保証つき）」に置く。
- **誰が使うのか**: 本プロジェクトの開発者・研究者（てんかん患者観察研究の映像解析パイプライン運用者）。
- **どこで使うのか**: gtune2 相当の CUDA GPU を持つ Linux 環境。phase4 の uv 環境（gsplat レンダ）と matcher_lab の uv 環境（MASt3R 推論）を subprocess 連携で併用する。

## 1.2 用語定義

機能設計書・コード内でも同じ用語を使う。

| 用語 | 定義 |
|---|---|
| アンカー対応点 | あるカメラのレンダ画像と実写画像を LoFTR でマッチし、レンダ側画素を深度マップで3D化した「3DGS座標系の3D点 ↔ 実写2D点」の対応。feat-026 の Stage2-3 と同一機構 |
| クロス対応点 | 2台のカメラの実写画像同士を MASt3R でマッチした「実写2D点 ↔ 実写2D点」の対応 |
| 採用ペア | クロス対応点の有効マッチ数が閾値以上のカメラペア |
| ブートストラップ | 初期ポーズ未知のカメラに対し、較正済みカメラとのクロス対応点＋較正済み側のレンダ深度リフトで 2D-3D 対応を作り、PnP で初期ポーズを得る処理 |
| 較正済み集合 | その時点で初期ポーズ（入力TOML由来またはブートストラップ由来）を持つカメラの集合 |
| BA | バンドル調整。全カメラの外部パラメータとクロス対応点の3D座標を同時に最適化する非線形最小二乗 |
| アンカー項 | BA の残差のうち、アンカー対応点の再投影誤差の項。座標系・スケールを3DGSモデルに固定する役割を持つ |
| クロス項 | BA の残差のうち、クロス対応点を三角測量した3D点の再投影誤差の項 |
| ホールドアウト | クロス対応点のうち最適化に使わず評価専用に取り分ける部分集合 |
| 3DGS座標系 | 入力 PLY（point_cloud.ply）の座標系。単位はメートル |
| K既知 | 内部パラメータ行列 K と歪み係数 D を入力TOMLの値に固定し推定しないこと |
| ポーズ確定 | `--init-cameras` で信頼指定された初期カメラ（案Aでは手動プロット + feat-026 で精緻化済みの全カメラ）。BA・評価・出力TOMLの対象はポーズ確定カメラのみ |

## 1.3 機能要求一覧

### FR-001 MASt3R ペアマッチング CLI

- **概要**: 画像2枚を入力し MASt3R でマッチ座標を NPZ 出力する CLI を matcher_lab に正式コンポーネントとして置く。
- **入力**: 画像A・画像Bのパス（PNG、1920x1080）、出力NPZパス、処理解像度オプション `--resolution full|1280x720`（既定 full。1280x720 指定時は CLI 内部で縮小して推論し、マッチ座標を原寸へ逆写像する。入力画像自体は常に原寸を渡す）。
- **出力**: NPZ（`u_a`, `u_b`: float64 (N,2) 原寸画素座標、`conf`: float32 (N,)、`meta`: JSON文字列）。終了コード 0=成功 / 42=CUDA OOM / 1=その他エラー。
- **受け入れ基準**: inuyama の実写2枚（cam05520125.png, cam05520126.png）に対して実行し、終了コード0で N≥1 のNPZが生成される。座標が全点 [0,1919]×[0,1079] に収まる。
- 既存の `docs/issues/feat-026-render-match-extrinsic-refinement/experiments/m3b_matcher/matcher_cli.py` の mast3r 経路と同等の実装を `matcher_lab/` 配下に移植する（実験フォルダのコードを本番から import しない）。

### FR-002 未較正カメラのブートストラップ（オプション経路。主経路では使用しない）

> **改訂（2026-08-18 案A）**: 対称環境での偽マッチにより全6台が誤収束したため（`experiments/p0_bootstrap/experiment_log.md`）、本機能は inuyama の主経路から除外する。実装済みコード（`bootstrap_cameras` ほか）は非対称シーン向けのオプションとして温存するが、本体 `main()` の主経路からは呼び出さない。`--init-cameras` に含まれないカメラが対象に存在する場合はエラーメッセージを出し終了コード1で終了する（案Aでは全対象カメラの初期ポーズが必須）。

- **概要**: 初期ポーズを持たないカメラに対し、較正済みカメラとのクロス対応点と較正済み側レンダ深度リフトから PnP で初期ポーズを推定する。手動基準点は入力に取らない。ブートストラップの成果物は**診断用途のみ**であり、ポーズ確定には一切使わない（案A。2026-08-17 の実測で単発 PnP のポーズはレンダ vs 実写 15〜43px のずれを持ち、さらに対称環境では偽マッチにより誤った位置に収束することを確認済み）。
- **入力**: 初期ポーズTOML（1台分以上）、初期ポーズを信頼するカメラ名の明示指定（`--init-cameras`。inuyama 主経路では**明示指定を必須**とする。省略時の「初期ポーズTOMLの全カメラを信頼する」規則は、全対象カメラ分のみを含む受理済みTOMLを使う場合に限る）、8台分の実写画像、PLY、内部パラメータTOML。
  - 明示指定が必要な理由: feat-026 の出力TOML（`refine_extrinsics.py` の `write_output_toml`）は入力TOMLの**全カメラ**のセクションを含み、精緻化されなかったカメラには無効な rotation/translation が残る。これをそのまま信頼すると未較正カメラが誤って較正済み扱いになる（2026-08-17 の Step 3 実測で顕在化した事象）。`--init-cameras` に指定されたカメラが初期ポーズTOMLに存在しない場合はエラーメッセージを出し終了コード1で終了する。
- **出力**: 全カメラの初期ポーズ（内部状態）。ブートストラップに失敗したカメラの一覧と失敗理由（対応点数不足 / PnP inlier 不足のいずれか）をレポートに記録する。
- **受け入れ基準**: inuyama データ（初期ポーズは cam05520125/126 の2台、残り6台は未較正）で、6台中1台以上がブートストラップに成功しレポートに成功/失敗が全台分記録される。失敗したカメラがあっても処理は継続する。

### FR-009 各カメラの反復精緻化（Stage R）【廃止】

- **廃止（2026-08-18 案A採用）**: 案Aにより全カメラの初期ポーズが手動プロット + feat-026 の精緻化済みポーズとなり、追加の反復精緻化の対象が存在しないため、本要求は実装せず廃止する（優先順位 Won't）。関連する状態（合意受理・品質受理）・CLI（`--stop-after-stage-r`, `--quality-accepted-cameras`）・2段階閾値確定手順も廃止する。経緯の記録として本節を残す。

### FR-003 アンカー対応点の取得

- **概要**: 各較正済みカメラについて、feat-026 と同一機構（レンダ→LoFTR→深度リフト→ゲート）でアンカー対応点を取得する。
- **入力**: カメラの初期ポーズ、PLY、実写画像、内部パラメータ。
- **出力**: カメラごとのアンカー対応点集合（3DGS座標系3D点、実写2D点、各カメラ N_A 点）。
- **受け入れ基準**: cam05520125/126 について N_A ≥ 30 のアンカー対応点が得られる（feat-026 の実績は数千点）。
- ゲート定数（GATE_ALPHA=0.5, GATE_Z_RANGE=(0.5,10.0), GATE_VAR_WINDOW=5, GATE_VAR_REL=0.02, NEAR_PLANE=0.5, ANCHOR_DISP_TAU_PX=10.0px〔feat-026 sched(1).tau_px、FR-008対象外〕）は feat-026 の値を初期値として流用する。

### FR-004 クロス対応点の取得とペア選定

- **概要**: 8台の全カメラペア C(8,2)=28 に対し FR-001 の CLI で MASt3R マッチングを実行し、有効マッチ数が N_PAIR_MIN 以上のペアを採用ペアとする。
- **入力**: 8台分の実写画像。
- **出力**: 採用ペアの一覧と各ペアのクロス対応点。全28ペアのマッチ数一覧をレポートに記録する。
- **受け入れ基準**: レポートに28ペア全てのマッチ数と採用/不採用が記録される。採用ペア数が0の場合はエラーメッセージを出力し終了コード1で終了する。

### FR-010 クロス対応点のエピポーラ整合フィルタ

- **概要**: 採用ペアのクロス対応点を、ポーズ確定カメラの確定ポーズ（K・D・R・t）から計算したエピポーラ幾何で選別し、対称構造の偽マッチを BA・評価に入れない。2026-08-18 の実測（対称偽マッチによる誤収束）で必要性が実証された防御機構。
- **入力**: ポーズ確定カメラの確定ポーズ、FR-004 の採用ペアとクロス対応点。
- **出力**: フィルタ後のクロス対応点。ペアごとの生存数・生存率をレポートに記録し、生存数 < N_PAIR_MIN となったペアは不採用に降格する（両端のいずれかがポーズ確定でないペアも不採用）。フィルタ後の採用ペアでグラフを構築し、**全ポーズ確定カメラが単一連結成分に入らない場合はエラーメッセージ（連結成分の内訳つき）を出し終了コード1で終了する**（多視点相互整合という主目的の前提。全ペア不採用も同様にエラー終了コード1）。
- **受け入れ基準**: inuyama 8台（全台ポーズ確定）で実行し、28ペア全てのフィルタ前後の対応点数・生存率・採用/不採用の再判定と連結性判定の結果がレポートに記録される。連結性不成立の場合の扱い（対象縮小 / EPI_TOL_PX 再検討 / 方針差し戻しのユーザー協議）はロードマップ Step 3F に事前定義する。
- エピポーラ許容誤差 EPI_TOL_PX の初期値は 3.0px とし、FR-008 の実験で決定する。

### FR-005 8台同時バンドル調整

- **概要**: BA参加カメラの外部パラメータとクロス対応点の三角測量3D点を、アンカー項＋クロス項の Huber ロバスト最小二乗で同時最適化する。K・D は固定（K既知）。クロス項の交会角重みは、FR-008 の実験（p1_param_sweep、2026-08-25。無効化 w=1 を含む比較）の採用結果により**主経路では無効化し w_k=1 固定**とする（当初案の最適角30°ガウス型スコア〔VISAPP2026 準拠、`prior_work.md` §2〕は本データで効果がなかった。三角測量の交会角ゲート TRI_MIN_ANGLE_DEG は維持する）。
- **BA参加条件**: **ポーズ確定カメラ**（用語定義参照）のうち、アンカー対応点数 N_A ≥ 30 のカメラのみ BA の最適化対象とする。フル実行時にポーズ確定カメラが2台未満の場合はクロス項が構成できないため、エラーメッセージを出し終了コード1で終了する。N_A < 30 のカメラはクロス項のみでは並進スケールが観測不能になり得るため BA に参加させず、信頼初期ポーズ（Step 3M の feat-026 受理済みポーズ）を最終値とし、レポートに「アンカー不足（BA未参加）」と記録する。
- **非悪化保証（BAフォールバック）**: BA 実行後、各 BA 参加カメラについてアンカー対応点への再投影残差中央値を「BA 前（信頼初期＝feat-026 精緻化済み）ポーズでの値」と比較し、**0.3px を超えて悪化したカメラは BA 前ポーズに戻す**（そのカメラの出力は信頼初期ポーズとし、レポートに「BAフォールバック」と記録する）。feat-026 品質より悪い結果を出力しないための保証。
- **入力**: ポーズ確定カメラのポーズ、FR-003 のアンカー対応点、FR-010 でフィルタ済みのクロス対応点（ホールドアウトを除く）。
- **出力**: 最適化後の全カメラ外部パラメータ。収束情報（反復数、初期/最終コスト）をレポートに記録する。
- **受け入れ基準**: inuyama データで最適化が収束し（scipy の status ≥ 1）、アンカー項残差の中央値（カメラ別）とクロス項残差の中央値（ペア別）が初期値以下になる。
- 座標系・スケールはアンカー項により3DGS座標系に固定される（追加のゲージ固定拘束は導入しない）。

### FR-006 ホールドアウト評価とレポート出力

- **概要**: クロス対応点の一部（比率 HOLDOUT_RATIO）を最適化から除外し、最適化後にホールドアウトの三角測量再投影残差を算出してレポートに出力する。
- **入力**: FR-010 でフィルタ済みのクロス対応点、FR-005 の最適化結果。
- **出力**: テキストレポート。記載必須項目: (a) カメラ別アンカー残差（中央値・RMSE。**BA前/BA後の両方**）、(b) ペア別クロス残差（中央値・RMSE）、(c) ホールドアウト三角測量再投影残差（中央値・RMSE）、(d) カメラ別の初期→最終ポーズ変化量（cm・度）、(e) ポーズ確定カメラ一覧と除外カメラ一覧、(f) 28ペアのマッチ数一覧、(g) 実行条件（入力パス、パラメータ値、シード、日時）、(h) エピポーラ整合フィルタのペア別生存数・生存率と採用再判定（FR-010）、(i) BAフォールバックの有無（カメラ別）。
- **受け入れ基準**: レポートに (a)〜(i) が全て出力される。
- 本案件では合格閾値による自動判定は行わない（測定値の報告まで。閾値は FR-008 の実験で今後決定する）。

### FR-007 出力TOML

- **概要**: 最適化後の8台分の外部パラメータを Calib_scene.toml 型（matrix, distortions, rotation, translation）で出力する。
- **入力**: FR-005 の最適化結果、内部パラメータTOML。
- **出力**: TOML ファイル。出力対象は**ポーズ確定カメラ**（用語定義参照。BA参加・BAフォールバック・アンカー不足によるBA未参加のいずれの経路でも、ポーズ確定カメラのポーズのみ）に限定する（除外カメラはレポートで明示する）。既存の `write_output_toml` は入力TOMLの全カメラを書き出す仕様のため流用せず、出力対象カメラのみを書く専用ライタを新設する。
- **受け入れ基準**: 出力TOMLを `render_keypoints.py` の `--no-keypoints --distort` 静止画モードでカメラ名指定して読み込み、レンダリングが成功する。

### FR-008 パラメータ決定実験（測定がゴールの実験）

- **概要**: N_PAIR_MIN、Huber スケール、アンカー項/クロス項の重み、HOLDOUT_RATIO、交会角重みの幅（THETA_SIGMA_DEG。無効化 w=1 を比較対象に含む）、および将来の合格閾値の候補値を決めるための試行実験を行う。任意の追加項目として、アンカー対応点のマッチャーを LoFTR から MASt3R に替えた比較（GS-CPR の先例に基づく）を criteria 作成時に採否判断のうえ含めてよい。ユーザー方針（閾値は試行錯誤で決める）に基づき、CLAUDE.md 実験プロトコルの「基準を測ることがゴールの実験」として criteria 文書に事前定義してから実施する。
- **入力**: inuyama データ一式。
- **出力**: `docs/issues/feat-035-multiview-extrinsic-bundle-adjustment/experiments/` 配下の criteria 文書と experiment_log。採用パラメータ値の記録。
- **受け入れ基準**: criteria 文書（測定ゴールとして定義）が実験実施前に Codex レビュー済みであること。採用値と根拠（交会角重みの採否〔σ値または w=1〕を含む）が experiment_log に記録されること。

## 1.4 非機能要求

- **パフォーマンス**: inuyama データ（8台、1920x1080）の全処理（マッチング28ペア＋BA＋レポート）が gtune2 環境で60分以内に完了する。
- **対応環境**: Linux + CUDA GPU 必須（gsplat レンダと MASt3R 推論）。phase4 実行時は環境変数 `TORCH_CUDA_ARCH_LIST="9.0+PTX"` を必須とする（CLAUDE.md 記載の既知事項）。
- **信頼性**: 途中失敗（1ペアのマッチング失敗、1台のブートストラップ失敗）で全体を中断しない。中間生成物（マッチNPZ）は tmp ディレクトリに保存し、レポートから実行条件を再現できる。出力TOML・レポートの上書きは `--overwrite` 指定時のみ許可する（refine_extrinsics.py と同一方針）。
- **セキュリティ**: 該当なし（ローカルバッチ処理）。

## 1.5 制約条件

- **使用必須**: Python 3.10（phase4）/ 3.12（matcher_lab）、NumPy、SciPy（`least_squares`）、OpenCV（`solvePnPRansac`, `triangulatePoints`, `projectPoints`, `Rodrigues`）、gsplat（レンダ）、MASt3R（`~/git/mast3r` + `~/data/models/mast3r/MASt3R_ViTLarge_BaseDecoder_512_catmlpdpt_metric.pth`。非商用研究用途のため NC ライセンス使用可）、kornia LoFTR（アンカー対応点）。
- **使用禁止**: 本スクリプトの自動処理では手動基準点CSV（kijunten_locations, points_2d）を最適化の拘束・スクリプト内の初期値生成・評価のいずれにも使わない（読み込まない）。**例外**: 外部の `refine_extrinsics.py` により手動点を用いて生成・**受理（accepted）された** TOML を `--init-toml` / `--init-cameras` として与えることは可（案Aの主経路そのもの。ロードマップ Step 3M）。受理されていないカメラのセクションを `--init-cameras` に指定することは禁止する。
- **環境管理**: uv のみ（`uv run --project phase4` / `uv run --project matcher_lab`）。pip / venv 直接操作は禁止。
- **ネットワーク**: オフライン動作（モデル重みはローカル既存のものを使う。新規ダウンロードなし）。
- **メモリ**: MASt3R が CUDA OOM（終了コード42）の場合は `--resolution 1280x720` を指定して1回だけ再試行する。
