# feat-030 要求仕様書: render_fps_video.py のチャンク並列レンダリング

- 作成日: 2026-08-10
- 準拠: `docs/REQUIREMENTS_STANDARD.md`
- 由来: feat-027 の旧FR-006（複数GPU並列）の後続。実験 e1（`experiments/e1_single_gpu_concurrency/`、Go 判定 R2=1.487）とヒアリング（`hearing-notes.md`、2026-08-10）に基づく

## 1.1 プロジェクト概要

- **何を作るのか**: `phase4/render_fps_video.py` の MP4 一括生成モードに、チャンク（区間MP4）を複数ワーカープロセスへ動的に分配して並列レンダリングする機構を追加する。
- **なぜ作るのか**: フルNPZ（約19.4万フレーム）の直列レンダリングは約70〜80分かかる。実験 e1 で、単一GPUでも2ワーカー並列で合計スループットが約1.49倍になることを確認した（GPU使用率36%→49%、律速はCPU側処理とCUDAコンテキスト時分割）。また本番環境（A100 サーバー、GPU 7枚）では複数GPUへの分配が必要になる。
- **誰が使うのか**: てんかん患者観察研究のデータ処理を行う研究者（本プロジェクトのユーザー）。
- **どこで使うのか**: ローカル機 gtune2（RTX 5060 Ti 16GB ×1、単一GPUに複数ワーカー）および A100 サーバー（GPU 7枚、SSH 直接実行・Slurm 非依存、別GPUに1ワーカーずつ）。

## 1.2 用語定義

| 用語 | 定義 |
|---|---|
| チャンク | フレーム数固定（`--chunk-size`、既定10000）で機械分割された区間。1チャンク=1つの自己完結の区間MP4（feat-027 で導入） |
| ワーカー | 1つのチャンクを丸ごと担当して逐次処理する子プロセス。1ワーカーは1つのGPU IDに割り当てられる |
| 分配 | 未完成チャンクをワーカーへ動的に割り当てること（早く空いたワーカーが次のチャンクを取る） |
| 直列モード | 従来どおり親プロセス内で1チャンクずつ処理する既存経路（feat-027 実装） |
| 並列モード | `--gpus` 指定時にワーカープロセス群で分配処理する本案件の新経路 |
| 再開 | 既存チャンクディレクトリの完成済み区間MP4（ffprobe 検査合格）をスキップして続きから処理する既存機構（feat-027 FR-007） |

機能設計書・コード内でも同じ用語を使う。

## 1.3 機能要求一覧

### FR-001: `--gpus` オプションによるワーカー構成の指定

- **概要**: カンマ区切りの非負整数リストでワーカー数と各ワーカーのGPU IDを指定できる。リストの要素数＝ワーカー数。同一IDの繰り返しで同一GPUへの複数ワーカー割当を表現する（例: `--gpus 0,0` = GPU 0 に2ワーカー、`--gpus 0,1,2,3,4,5,6` = 7GPUに1ワーカーずつ）。
- **入力**: CLI `--gpus <カンマ区切り非負整数>`、または設定YAML（feat-029）のキー `gpus: <同形式の文字列>`（CLI優先の既存規則に従う）。
- **出力**: 起動ログにワーカー構成（ワーカー数と各GPU ID）を表示する。
- **制約**:
  - `--gpu` と `--gpus` は排他。両方指定された場合（YAML経由の指定を含む）はエラーメッセージを表示し終了コード2で終了する。
  - `--gpus` は MP4 一括生成モード専用。`--still-range` / `--dump-poses` と同時指定された場合はエラーメッセージを表示し終了コード2で終了する。
  - リスト内の各GPU IDが `torch.cuda.device_count()` 未満でない場合はエラーメッセージを表示し終了コード1で終了する。
  - 形式不正（空要素、非整数、負数）はエラーメッセージを表示し終了コード2で終了する。
- **受け入れ基準**: 上記の正常系1件（`--gpus 0,0` で2ワーカー起動）と異常系4件（--gpu併用・排他モード併用・範囲外ID・形式不正）が仕様どおり動作する。

### FR-002: チャンクの動的分配による並列レンダリング

- **概要**: `--gpus` 指定時、未完成チャンクをワーカープロセス群へ動的に分配し、各ワーカーが割り当てGPU上でチャンクをレンダリングして区間MP4を確定する。全チャンク完了後、親プロセスが既存の連結処理（feat-027 FR-008）で最終MP4を生成する。
- **入力**: 直列モードと同一（PLY・NPZ・TOML・レンダリングパラメータ）。
- **出力**: 直列モードと同一の最終MP4。チャンク内部の処理（レンダリング・エンコード・durable_replace）は既存の `render_chunk()` を無改変で使うため、各区間MP4の生成過程はワーカー数によらず同一である。
- **受け入れ基準**:
  1. `--gpus 0,0` の出力MP4のフレーム数・解像度・チャンク構成が直列モードと一致する。
  2. 実験 e1 と同条件（tiled 3000フレーム・chunk_size 500・1920x1080・crf 18・preset medium・RTX 5060 Ti）で、`--gpus 0,0` の合計スループットが直列モードの1.3倍以上である。測定方法は実験 e1 と同一とする（チャンク完了ログの所要秒から、ウォームアップ分＝直列は先頭チャンク・並列は各ワーカーの初回チャンクを除外して秒/フレームを算出し、逆数和の比を取る。閾値1.3は e1 の R2 算出式に対して定義された値のため同じ式で判定する）。

### FR-003: 並列モードと再開機構の互換

- **概要**: 並列モードでも既存の再開機構（マニフェスト検証・完成済みチャンクの ffprobe 検査・スキップ）がそのまま働く。ワーカー構成（`--gpus` の値）はマニフェストの照合対象に含めない（直列で始めた処理を並列で再開する、およびその逆、ワーカー数の変更がいずれも可能）。
- **入力**: 既存チャンクディレクトリ＋ `--gpus` 指定の再実行。
- **出力**: 完成済みチャンクはスキップされ（スキップログ表示）、未完成チャンクのみ分配される。
- **受け入れ基準**: 直列モードで一部チャンク完成後に中断→ `--gpus 0,0` で再実行した場合に、完成済みチャンクがスキップされ最終MP4が生成される。

### FR-004: ワーカー失敗時の即時中止

- **概要**: いずれかのワーカーがチャンク処理に失敗した場合、親プロセスは残りワーカーを停止し、エラーメッセージを表示して終了コード1で終了する。書きかけの `.tmp` ファイルは削除する。完成済み区間MP4は保持し、再実行で続きから再開できる。
- **入力**: ワーカー内の例外（ffmpeg異常終了、CUDA エラーを含む処理中の全例外）またはワーカープロセスの異常終了（終了コード非0）。
- **出力**: stderr に失敗ワーカー・失敗チャンク番号・原因を表示。終了コード1。
- **受け入れ基準**: 失敗イベント発生時に「全ワーカー停止・終了コード1・チャンクディレクトリに `.tmp` が残らない・完成済みチャンクが保持される」ことを、分配ループ単体の自動テスト（フェイクのワーカー・キューを注入）で検証する。実GPU上の実挙動（実行中のワーカープロセスを kill した場合の即時中止と再開）は手動テストで確認する。

### FR-005: 並列実行の進捗ログと集計

- **概要**: 並列モードでは各チャンク完了ログにワーカータグ（`[W0]`〜）を付け、どのワーカー（どのGPU）が処理したか判別できるようにする。全体完了時に描画フレーム総数・描画フレーム平均秒（全ワーカー合算）を表示する。
- **入力**: なし（内部イベント）。
- **出力**: stdout。起動時「並列: Nワーカー（GPU割当: ...）」、チャンク完了ごとに「[Wk] チャンク NNNNN (fid F-F) 完了: 描画 n/N フレーム, S.S秒」、正常終了時に「ワーカー描画時間合計: S.S秒（実効 S.S秒, Nワーカー）」、完了時に既存形式の総所要・平均のサマリ（並列時の「描画フレーム平均」は wall-clock 実効秒/フレームとする。ワーカー別所要秒の単純合算は実効スループットを表さないため平均算出に使わない）。
- **受け入れ基準**: `--gpus 0,0` 実行のログに、ワーカータグ付きチャンク完了行が全チャンク分と、最終サマリ行が出力される。

## 1.4 非機能要求

- **パフォーマンス**: FR-002 受け入れ基準2のとおり（ローカル2ワーカーで直列比1.3倍以上。実験 e1 実測 1.487倍に基づく）。それ以上のワーカー数・複数GPUでの性能値は本案件では規定しない（A100 実機は本案件のテスト環境外）。
- **対応環境**: Linux、CUDA GPU 必須（並列モードは指定した全GPU IDが有効であること）。ローカル機は `TORCH_CUDA_ARCH_LIST="9.0+PTX"` が必要（CLAUDE.md 参照）。VRAM はワーカーあたり約630MiB（e1 実測、session001 PLY 139MB の場合）を要する。
- **信頼性**: チャンク確定は既存の durable_replace（fsync→replace→dir fsync）、再開時破損検査は既存の ffprobe 検査を無改変で流用する。並列化による信頼性の低下がないこと（チャンク書き出し経路に変更を加えない）。
- **セキュリティ**: 該当なし。

## 1.5 制約条件

- 使用ライブラリ: Python 3.10 標準ライブラリの `multiprocessing`（新規外部依存を追加しない）。torch / gsplat / numpy / ffmpeg は既存のまま。
- 既存の直列モードのコードパス・出力・ログ形式を変更しない（`--gpus` 未指定時の挙動は feat-027/029 完了時点と同一であること。既存 pytest が無修正で通ること）。
- `durable_replace()`・`verify_chunk_mp4()`・`concat_chunks()`・マニフェスト関数群は無改変で流用する（チャンク処理の等価性を保証するため）。
- `render_chunk()` は正常系（フレーム描画・エンコード・durable_replace までの経路）を無改変で流用する。**例外として、KeyboardInterrupt 捕捉節（異常停止時の後始末）に限り、ffmpeg 停止を確実化する変更（stdin クローズ → terminate → タイムアウト付き wait → kill エスカレーション）を認める**。理由: 実装フェーズのGPU実機確認3（2026-08-10）で、SIGTERM 停止時に stdin 未クローズのまま `terminate(); wait()` すると ffmpeg がパイプ読み取りブロックのまま終了せず、ワーカーが `wait()` で永久待機するデッドロックを実機で確認したため。この変更は正常系の出力に影響しない（設計書 §4.7）。
- Slurm・ジョブスケジューラに依存しない（A100 サーバーは SSH 直接実行）。
