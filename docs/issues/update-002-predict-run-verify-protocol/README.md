# update-002: 「予測→実行→照合」プロトコルの開発ルール組み込み

## ステータス

Open（2026-08-03 起票）

## 概要

feat-026 で試験導入した「予測→実行→照合」プロトコル（実験・検証の判定基準を実行前に数値で定義し、各フェーズの直前に予測を記録してから実行し、実測と照合する運用）を、開発ルール（`CLAUDE.md`）に正式に組み込む。

## 背景・変更理由

- feat-026 の M1 実験（2026-07-31）で、未実証の閾値（収束域「数cm・数度」）と未定義の合格ラインのまま実験を実行し、結果を見てから「条件付きGo」と事後解釈した。ユーザーから「基準がないのに RANSAC が効く・効かないを論じても意味がない」「分からないことは分からないと明示せよ」と指摘され、判定を撤回した
- 以降の M2〜M4・M3b の全実験で本プロトコルを適用し、有効性が確認された（試験導入）。ユーザーの指示により開発ルールへの正式組み込みを行う（update-001 の後続案件として計画済み）
- 現行の `CLAUDE.md` には実験・検証の進め方に関する規定がなく、プロトコルは feat-026 案件フォルダ内の実験文書とセッションメモリにしか存在しない

## 調査: feat-026 での実運用（プロトコルの内容）

feat-026 の実験ディレクトリ（`docs/issues/feat-026-render-match-extrinsic-refinement/experiments/`）で確立した運用は以下のとおり。

1. **判定基準の事前定義**: 実験ごとに criteria 文書（`criteria.md`, `criteria_m4_1.md` 等）を作成し、「答える問い」「判定閾値」「合格ライン」を実行前に数値で確定した。criteria 文書は実行前に Codex レビューを収束させてから実験を実行した（criteria lock 方式）
2. **直前予測**: 各フェーズの実行直前に予測（数値）を `experiment_log.md` に記録してから実行し、実測と照合した。criteria 文書には「予測の枠」（フェーズ直前に数値を確定して記録する項目の一覧）だけを事前定義し、値はフェーズ直前に埋めた（例: `criteria_m4_1.md` セクション8）
3. **予測は前段の実測を使って直前に立てる**: 全フェーズ一括の事前予測はしない（前段の結果で後段の内容が変わるため）
4. **照合と乖離時の扱い**: 予測と実測が乖離したら、そのフェーズの前提・理解を疑うシグナルとした
5. **事後解釈の禁止**: 基準のない実験は「測定」であって「判定」ではない。M1 の「条件付きGo」撤回がこの原則の起点

## 変更方針

### 掲載先の選定

| 候補 | 判断 | 理由 |
|---|---|---|
| `CLAUDE.md` の「開発方針」配下に節を新設（**採用**） | 採用 | プロトコルは feat/bug 案件の調査フェーズ・手動テスト調査を横断する開発の進め方であり、フロー定義群と同じ場所に置くのが自然。分量も1節で収まる |
| 新規基準書 `docs/EXPERIMENT_STANDARD.md` | 不採用 | 現時点の内容は1節分であり、独立ファイルは過剰。将来、実験文書の書式（criteria 文書の必須セクション等）まで標準化する需要が出たら分離を検討 |
| `docs/REVIEW_CRITERIA.md` への追記 | 不採用 | REVIEW_CRITERIA はレビューの観点集であり、作業の進め方（プロトコル）の定義場所ではない。update-001 でテンプレートと完全一致にしたばかりで、プロジェクト固有の追記は乖離を生む |

### 挿入位置

`CLAUDE.md` の「### ドキュメント更新フロー（update-XXX 案件）」（運用メモ含む）の直後、「### ドキュメント作成ルール」の直前。3つの案件フロー定義の後に、フロー横断の進め方ルールとして置く。

### 適用範囲の定義

プロトコルの適用対象は「**数値判定を伴う実験・検証**」（案件の調査フェーズでの実験、閾値・パラメータの妥当性検証、性能測定等）に限定する。以下は対象外とし、その旨をルール本文に明記する:

- 通常の実装・自動テスト（pytest はテストコード自体が期待値＝予測の文書化に当たり、二重の予測記録は冗長）
- 数値判定を伴わない調査（コード読解、ドキュメント調査等）

### 記載しないこと

- criteria 文書・実験ログの詳細書式（必須セクション等）の標準化 → 現時点では feat-026 の実例参照で足りる。需要が出たら別案件で基準書化
- feat-026 実験文書の遡及修正 → 完了案件であり不要

## 実施しないこと

- ソースコード・テストコードの変更（本案件は CLAUDE.md と完了処理のみ）
- ルート README.md の変更（コマンド・CLIオプション・入出力形式に変更なし）
- `docs/REVIEW_CRITERIA.md` 等の基準書の変更
